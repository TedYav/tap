Teams across projects

A team in one project can ask another team about the code it owns.

HomeLevel 1Level 2Level 3Level 4Level 5Skills

What you can do

Ask the API team whether a field rename breaks clients. Have a web team request an example response. Let a shared-library team review a caller’s proposed change while each team keeps its own project context.

Try it

Use two existing projects whose directories are named api and web. In your terminal, replace these paths with yours:

cd /path/to/api
tap init
tap launch codex reviewer

If the reviewer opens, press Ctrl-b, then d to return to your shell before switching projects.

cd /path/to/web
tap init
tap launch claude builder

Tell the builder:

Ask api/reviewer whether renaming user_id to account_id in the export breaks a client. Show me the answer before changing anything.

From your terminal, after detaching:

tap teams
tap team roster api
tap attach api/reviewer

What’s new since level 2

An address gains a team name: team/seat. A team is named after the project directory when you initialize it. The agent’s question uses tap send api/reviewer --ask -f question.md, with its question saved in that file.

The answer still returns to the asking seat. Seeing the other team on the roster does not establish that it read your request. TAP connects these projects on the same machine.

Go deeper

The command reference covers team addresses. Visiting a seat helps when an answer is waiting on a prompt.
