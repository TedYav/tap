## Envelope (payload frontmatter)

Five routing fields — `id`, `from`, `to`, `kind`, `path` — plus optional `re:` and any writer extras (preserved verbatim, EXCEPT the courier-owned optional fields below, which are never trusted from the writer — see below). The **courier owns the five routing fields**: a writer may omit `id`/`path` entirely, and `tap send` stamps all five into the _canonical_ payload (`stampEnvelope`, runtime/bun/src/envelope.ts) BEFORE `validateEnvelope` checks it inside `canonicalPlaceLocked` (runtime/bun/src/courier.ts), so the on-disk payload can never disagree with the injected sentinel. Resolution precedence: `id` = `--id` > frontmatter > minted; `from` = `--from` > `TAP_SELF` > pane-derived handle > fail loud; `kind` = `--kind` > frontmatter > `discuss`; `to` = the positional send target; `path` = the canonical `payloads/<id>.md`. The resolved `from` must name an active sender on the sender-team registry: active pane seat or active `delivery: poll` seat. Unknown/suspended `--from` is refused with poll-seat registration guidance; the reserved watcher identity is the narrow supervisor exception for `kind=probe|notice|progress` settle-only traffic. A readable positional file that does not open with a `---` fence is treated as fenceless markdown: `tap send` wraps it with an empty frontmatter block before stamping. A file that does open with `---` must still provide a valid closing fence; malformed fenced payloads fail closed. Positional text that is not an existing file is rejected with a shell-quoted `-m` correction. An inline `-m` body is bounded by `TAP_INLINE_MAX_BYTES` (default 102400 bytes; the `payload_too_large` refusal names the file form, which has no limit), read at send time by the one construction module both doors call (D1), with Bash's `[ -gt ]` integer grammar — an optional sign then digits, so `+5`, `-1` and `0005` are caps — and printed back as the operator spelled it. Surrounding whitespace is trimmed before matching, so a value with a trailing line ending (`5<LF>`) is a cap on every build and both doors. A value outside that grammar is the default cap on both doors: the incumbent Bash `[ -gt ]` errored on it and skipped the check (a note over the default cap went out), and that skipped check no longer exists on either door — a measured deviation ratified with D1. **TAP validates SHAPE only** (`validateEnvelope`): `kind` must be present + non-empty, but general kind vocabulary belongs to orchestration, with the explicit supervision and escalation exceptions below. Transport treats general kinds as vocabulary, but reserved supervision kinds and `escalate` have the explicit delivery-policy rules documented below. If AESOP needs priority/control routing, it does so structurally (e.g. a `priority/` dir), never by teaching the courier to read the mail.

**Known optional fields (not required, never TORN when absent):**

- `cross_worktree: true` — stamped by cross-worktree sends (team-qualified remote sends and manual `--cross-worktree` sends); absent on normal same-team sends (back-compat). Enables `tap outstanding` to label the item `[cross-worktree]` without consulting a registry. `tap doctor` registers this as a known optional field; it is never flagged as torn or unknown.
- `from_team: <team>` — **courier-owned-when-present** (tap-yv3, codex P1): `stampEnvelope` unconditionally drops any writer-supplied `from_team` from the source payload, then re-stamps its own resolution (non-empty on any cross-team send, since the sender's own team is always known once cross-team addressing is in play; absent on same-team traffic). Never trust a writer's copy — `poll`/`outstanding`/`health` display it and a reply can address off it, so a surviving spoofed value would misroute a reply, not just mislabel a display. Lets the recipient reply with `tap send <from_team>/<from> ...` while the canonical `from`/`to` fields stay team-local handles.
- `to_team: <team>` (v0.4; recipient authority hardened in v0.12) — **courier-owned-when-present**, same authority and same drop-then-restamp rule as `from_team`. Stamped **symmetric with `from_team`** but only when team-qualified addressing resolved it (i.e. `TARGET_TEAM` is known); absent on a manual `--cross-worktree --pane` send (no registry lookup happens on that path, so the target's team is unknowable — a writer-supplied `to_team` there is dropped outright, never surfaced) and on same-team traffic. It is the team half of recipient authority: inbound views and settlement require it to match the local team name resolved from the **global enrollment key** (`context.ts` `spoolTeamName` / `ctx.team`) — never the acting document's `team.name` nor the worktree basename — before comparing the bare `to` handle (see also §Cross-worktree relay, `delivery/cross-worktree-relay-unit-2b-part-02.md`). It also lets `tap outstanding`/`tap health` render `<to_team>/<to>` without a registry round-trip (§Sentinel, §Cross-worktree relay). `tap doctor` registers it as a known optional field.
- `reply: expected|settle-only` — the sender-declared reply expectation (§Reply expectation). Stamped on every v0.3 send; **absent on old v0.2 traffic reads as `expected`**. `tap doctor` registers it as a known optional field; it is never flagged as torn or unknown.
- `urgency: urgent` (PR-B) — **courier-owned-when-present**, stamped only on `tap send --urgent` (absent on default/polite, same present-only-when-relevant pattern as `to_team`). Informational: the recipient's context for why its turn was interrupted. `tap_reconstruct_sentinel` carries it through for a spooled-then-redelivered urgent entry even though that redelivery is a plain (non-interrupting) injection (§Delivery policies). `tap doctor` registers it as a known optional field.
- `reply_to: <team>/<handle>` (tap-ywb, v0.5; team binding hardened in v0.6) — **courier-owned-when-present**, same drop-then-restamp discipline as `from_team`/`to_team`: a writer-supplied copy is always dropped, never trusted (§Reply routing, below). CLI/registry input may still be bare `<handle>`, but the courier resolves that bare handle against the **sender's bus at send time** and always stamps the qualified `<team>/<handle>` identity. This prevents a recipient on another team from resolving the same bare handle against its own registry at reply time. Stamped from an explicit `tap send --reply-to`, or absent that, from the `--from` seat's own registered `reply_to` (`register --unattended --reply-to`, auto-stamped on every plain send from that seat) — EXCEPT `tap reply`'s own courier-composed outbound, which always passes `--no-auto-reply-to` to suppress the ACTOR's seat default (panel MUST-FIX 2: without this, the actor's own follow-up channel would silently ride onto someone else's reply). The address must be DELIVERABLE (`tap_seat_deliverable`, not mere existence — MUST-FIX 1) at stamp time; an explicit `--reply-to` refuses hard on failure, a stale registry-derived default soft-fails (warn, omit, send anyway — MUST-FIX 3). Present only when set; absent means "reply to `from`, as always." No `reply_to_team` split field is needed. `tap doctor` registers it as a known optional field; it is never flagged as torn or unknown. No sentinel change — this field is never carried into the `[[TAP ...]]` sentinel; routing off it happens at `tap reply` time, reading the canonical payload directly (`tap poll`'s payload-derived display surfaces it when present, poll-only per the panel's split ruling — the sentinel itself stays unchanged). Legacy hand-authored/pre-v0.6 bare envelope values remain readable relative to the replier's bus, but new couriers never emit them.
- `in_reply_to: <inbound-id>` (tap-qnpn) — **courier-owned-when-present**, stamped only on the canonical outbound composed by `tap reply`; ordinary sends unconditionally drop a writer-supplied copy. It correlates the reply payload to the inbound that its eventual `.done` settles. The field is envelope-only (no sentinel change), and the private reply-settlement path in `tap-done.sh` requires it to equal the inbound id before writing `via: reply` evidence.
