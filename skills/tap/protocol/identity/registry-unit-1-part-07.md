Crew are transport members but not independently relaunchable sessions. A crew row is live when its recorded `pane_id` is present on the current tmux server and its `server_epoch` matches the live epoch; any other state is residue. `tap team refresh` (plain and `--hard`) deletes a crew row whose pane is dead, whose `pane_id` is empty, or whose status is `suspended:server_restarted` — keyed on the pane, not on the parent session. A crew row whose pane is alive but whose harness exited, or whose pane moved address, is kept (fail-closed). Session-killing verbs (`tap team down`, `shutdown`, and per-seat stop) delete the crew rows of every session they kill, reporting the collection; `tap team up` (`session resume --all`) excludes crew and never resurrects them. After `down`, the roster contains exactly the handles `up` can restore. At that shared stop boundary, `tap team down` and `tap team shutdown` disarm the watcher lease (the `tap watch off` locked delete) before roster removal; a partially refused stop still disarms once past its mutation boundary, while queued reminders and pending escalations (`watch/reminders.json`, `watch/notify.json`) are preserved.

Crew handles are not sparable units for session verbs. `--only <crew>` and `--except <crew>` on `down`, `up`, `shutdown`, `attach`, and `detach` are `error_class=usage_error` naming the parent handle and `tap crew remove <crew>` as the recovery action. `--only <teammate>` plans the session kill and collects that teammate's crew (once, even if both are named).

**Linked worktree enrollment.** `tap session launch` refuses an unenrolled linked Git worktree before creating a bus, registry row, or harness process, even in `--dry-run`; the refusal names the team it would create. Launch from an enrolled team root or enroll the worktree with `tap register` first. Enrolled worktrees continue normally; a primary repository may still bootstrap its first team.

**Tmux deadlines.** The default shared Bash tmux client and Bun adapter bound observations to five seconds and other noninteractive calls to ten seconds. `TAP_TMUX_TIMEOUT_SECONDS` accepts a finite 0.01–60s override; invalid values retain the default. Interactive attachment/control clients stay interactive; pre-existing injected Bash functions keep their own socket routing and client policy. Timeout reports `server_unresponsive`, the socket, the known server PID (or `unknown`); an unknown effect. A nonzero tmux client result containing `fork failed: Device not configured` also reports `server_unresponsive`, with the socket, known server PID and one-minute load (`load1m`); Bash returns 124 and Bun throws the same typed refusal. The shared adapters make no retry and never read the refusal as pane loss. A timed-out `send-keys` stops without another inject, courtesy Enter, or spool retry; the canonical payload remains available without a verified-delivery receipt. Doctor reports failed responsive probes as `server_unresponsive`, not proof of an orphaned server.

**Clear recipe identity.** `tap clear` (and peer `tap refresh --fresh`) builds its fresh invocation from the addressed registry row, including crew rows that share a parent's tmux session. A missing or unknown harness refuses before replacement; the parent session never supplies a fallback recipe. Crew add records the resolved model, environment, passthrough and preset provenance against its just-registered pane before starting the harness. Existing nonce, rebind and remain-on-exit controls still govern.

**Process session recovery.** Claude may also supply its current session via `~/.claude/sessions/<pid>.json`: the PID, UTC process start time, worktree and interactive kind must match the unique pane-owned process, and the record and process generation must stay stable across observation. This covers idle transcripts not held open. Stability checks cover the harness and its ancestor chain back to the pane; unrelated tool children may finish during observation. Launch argv alone never establishes current identity after clear or resume.

**Bound store checks.** Doctor checks OpenCode's registered ID/worktree in its SQLite store and Cursor's exact chat store under the workspace hash, keyed on the seat's harness workdir (launch, else registered). These checks report `unchanged` with a bound-store detail; they neither identify the current conversation nor repair IDs. Pane/namespace checks still apply.

**Operator session repair.** `tap team doctor` uses this process evidence to update a current active seat's session ID and transcript path together. Under the reset and registry locks it rechecks the unchanged row, pane generation, process/session evidence and the duplicate-owner check. Ownership is structural: the pane's topmost harness-named descendant owns the session; nested namesakes never split it, siblings stay ambiguous. It preserves instance, delivery and custody and records the previous binding under `identity_capture_result` (`mode: operator_rebind`), superseding old capture/quarantine fields. Inactive, ambiguous and duplicate-owned sessions stay unchanged; reporting never writes. `--fix` applies verified repairs; `--only session-binding` selects it. JSON keeps the `{ok, bus, findings, summary}` envelope and warning exits (0: completed scan with advisory findings; 1: errors). Human output groups skips under yellow `not checked` warnings, each naming a next step; repair findings stay red. OpenCode uses compact's store preflight: invalid bindings are red, outcome `invalid`, and `summary.clean=false`; no repair is guessed.

**Process session recovery (open files).** When environment capture is empty, registration may recover Codex or Claude identity from exactly one per-session file held open by the matching harness process beneath the observed pane PID. The process ancestry and start time must not change across the bounded observation. Codex rollout metadata must match the worktree and filename ID; the process working directory must be observable and equal the expected worktree — gating the open-file path for both harnesses — else the observation refuses. Claude requires an exact project transcript. Successful capture records `session_attribution_trust=process` and passes the expectation and duplicate-owner guards; `tap in` from the live seat pane captures it before relaunch. Unavailable, changed, dead, or ambiguous observations supply no process identity (use the harness picker), and recency never disambiguates. OpenCode's shared database is non-authoritative and cannot supply an exact resume ID.

**Direct harness identity (optional, pane seats only).** `harness_session_id` precedence: explicit `--harness-session-id <id>` > pane-native env > generic `TAP_HARNESS_SESSION_ID` > exact process-held session file above. SessionStart passes the operand only for nonempty JSON identity, idempotently registers the pane, then the harness-local adapter updates only the exact acting-registry root+handle+harness row; cross-harness variables and newest-file scans are ignored. A launcher-created or exact-resume capture may set or rotate the field. Picker/latest/adopted capture, missing expected identity, unattested change, or cross-seat duplication writes quarantine fields and a warning instead; registration still succeeds, and empty values never clear trusted provenance. OpenCode binds through its SessionStart-equivalent plugin: a new row starts id-less, then `tap in` captures the root TUI's `OPENCODE_SESSION_ID`. A later exact resume carries that id as the launch expectation; store-derived candidates never become exact authority. **A launcher-expectation quarantine is WITHDRAWABLE by the operator** (tap-zqcd): `tap register <h> --accept-observed-identity` retires the standing expectation and accepts the observed id, recording `retired_expectation` and `mode: operator_accepted` on the capture result, so it never reads as attested. It is scoped to that class alone; a duplicate-owner refusal is a fact about another seat and no operator statement clears it. A launcher expectation is ALSO retired without an operator, on a seat's own self-attested `clear`, `compact` or `fork` SessionStart, recording `mode: self_attested_rebind`, never `operator_accepted`: a provenance record must not claim a human act. It is admitted only when the seat reports a DIFFERENT id from the one its row acts on, from its own environment rather than store attribution, and from a process proven by ancestry to run under the registered pane; `startup` and `resume` are excluded, and a duplicate-owner refusal still clears nothing.

**Launch-time pre-mint (tap-e9v8; tap-ql59z).** Cursor's `cursor-agent create-chat` returns a UUID reservation; the builder uses `--resume <id>` for launch, clear (`action=new`) and resume when the record holds it (tap-rs1q; tap-xsgi twin). The reservation stores `identity_capture.expected_harness_session_id`, `mode=launcher_new`; Cursor mint failure permits an id-less launch. OpenCode 2 prepares sessions through its API ([fallback rules](registry-unit-1-part-08.md)). Claude and Codex retain deterministic capture via `--session-id` and rollout capture respectively; neither is pre-minted.

**Exact-team read scope (tap-7s1r, v0.23).** `enrolledSeatForObservedPane` accepts an optional exact-team scope applied before any stat or read: a scoped call skips every other team's entry, so another team's missing or unreadable registry never tips a valid in-scope claim into "uniqueness unproven". A scoped verdict is NOT proof of global uniqueness: the pane-anchored context also reads unscoped, before the repository probes and after the final scoped read (tap-sbvgt); either read's `contested` or `unverified` verdict (an unreadable enrolled registry leaves uniqueness unproven) fails the anchor like any miss, keeping the saved refusal while the verb recomputes `pane_contested`; only a verified outcome leaves scoped resolution standing. Modern resolved rows carry the registry location that supplied them and bind final selection to it; the legacy arm stays unchanged. The default unscoped path is byte-identical to the incumbent.

**Stale enrollment is the stale team's problem (tap-xbpuc).** An enrolled team whose acting registry is positively absent (ENOENT, e.g. a worktree removed while enrolled) holds no seat rows, so it never vetoes another team's unique claimant; an unreadable registry still leaves uniqueness unproven (`pane_unknown`; the pane was observed, so the detail leads with the team, not tmux, and the hint says repair it; a missing, empty or non-string `registry_location` is its own `malformed_enrollment` (repair the enrollment, not the registry; an unreadable registry beside it keeps its hint); a malformed claimant root has its own hint; only a missing generation stamp keeps the tmux wording), and an old-format one is never read: the lookup names that team in its own `old_store` verdict, never `tap register`. With no readable claimant, a pane whose canonical `team/handle` session names a data-gone team refuses `error_class=stale_enrollment` (the session picks the refusal, not identity), as does a send to `<team>/<handle>`; both name `tap admin refresh`. A present but unreadable location stays `unreachable_team`. Sends never de-enroll: `tap doctor --fix` prunes root-gone rows (tap-k140: snapshot first; failure prunes nothing), `tap admin refresh` purges data-gone rows, `tap admin retire <team>` de-enrolls one, and `tap worktree check` names `tap team shutdown <team>` for an enrolled root (stops seats, de-enrolls).

Human doctor output omits unchanged seats and prints `✓ no issues detected` with no visible findings. Interactive terminals show transient current-seat progress; warnings stay red, the clean check green. Color honors `NO_COLOR`; progress needs terminal stdout and stderr, and both are off for `TERM=dumb`. Redirected and JSON output drop terminal controls; JSON retains all findings.
