## Seat clear (`tap clear`) (v0.21)

`tap clear <seat> [-m <instruction>] [--dry-run]` **replaces a seat's harness process inside the pane it already occupies**, clears that pane's scrollback, and lets the fresh process's own registration rebind the handle. It starts a **new conversation**; it does not resume one.

**Native clear (R7b).** `tap clear` has one owner, `cmdClearNative` in `runtime/bun/src/launcher/replace.ts`, on every door: the public router runs it in-process without a restart-reconciliation prelude, and `tap refresh` calls the same function in-process for its clearing step, so no process boundary separates policy from engine. Its grammar, refusals, exit codes and `--dry-run` output are the retired `tap-clear.sh` / `launcher.py clear` pair's. `tap session relaunch` calls the same Bun replacement core with exact-conversation readiness instead of fresh-registration verification; the Python replacement transaction is retired.

**Without `-m`, a clear PARKS the seat.** Clear delivers no rebind recap by design — reconciling a seat with the obligations it inherited is `tap refresh`'s job, not this verb's — so a seat cleared with no first instruction comes back oriented by nothing and waits. That is correct behavior and a caller obligation, not a gap: either pass `-m`, or address the seat immediately afterwards. Reported from the field by the first production consumer of this verb, which was itself the cleared seat (tap-thgv run).

**A stillborn harness must not take the pane with it.** Production seats run with `remain-on-exit` off, so a process that fails on the way up would take the pane with it — and a single-window seat's session too — turning a restart into exactly the identity loss this verb exists to prevent. `tap clear` therefore arms `remain-on-exit` **before** the respawn and disarms it after the rebind wait, leaving a failed start as a pane that is PRESENT but exited: readable by the operator, still nameable by the registry. **If the arming itself fails the verb warns loudly and proceeds** — a flaky `set-option` should not brick a restart the operator asked for — but it never proceeds silently, because a protection this spec promises and does not deliver would otherwise be discovered by losing a seat. The respawn also passes the seat's recorded cwd, because the pane's directory follows whatever the previous process changed it to and registration resolves the bus from cwd.

Cancellation and uncertain arming also run the disarm, under the still-held clear fence, with a fresh two-second deadline that does not inherit the cancelled work signal. Cleanup first rechecks the pane id and server generation; an unobservable or changed binding refuses the option change. A failed disarm remains a loud warning in the command diagnostics and relaunch receipt, and interrupted outcomes retain the possible-option-change warning. No cleanup path retries respawn. Forced process death can prevent in-process cleanup; an absent disarm receipt is not proof that retention is off.

**Respawn in place, never a new window — this is the load-bearing decision.** Registration is pane-bound, so a restart into a *new* pane leaves the SessionStart hook with no binding for that pane, and its collision-avoidance mints a suffixed handle (`opus` → `opus-3`) before any rebind step can run. That is not a race to be won by ordering; the fork is decided by construction, and a post-hoc rebind cannot beat it. `tmux respawn-pane -k` replaces the process while keeping the pane object, so the pane id survives, the registry binding stays valid, and the seat keeps its identity — the same path a user-typed `/clear` takes. `tmux clear-history` then recovers the fresh-buffer benefit a new window would have given for free.

**The rebind is verified by a nonce, not by the pane binding.** Because respawn-pane preserves the pane id deliberately, `handle -> pane id` is equally true before the clear, after it, and when the respawn silently did nothing — a predicate satisfied by its own failure case verifies nothing. `tap clear` therefore mints a per-clear nonce, writes it to the seat's row as `expected_clear_nonce` **before** the respawn, and passes it to the fresh process as `TAP_CLEAR_ID`. Registration records the value it observes as `clear_nonce`, and the verification requires that field to be **present and equal**, alongside the expected pane id and `status=active`.

**Registration records `clear_nonce` ONLY when it answers a pending question** (`expected_clear_nonce` set and equal). A process carrying no `TAP_CLEAR_ID` still REMOVES `clear_nonce` — that is the witness-removal half, and when `TAP_REGISTER_SUPPRESS_IDENTITY_CAPTURE=1` marks a registration running in another agent's environment the env is blanked first so this path is taken. **Registration never pops `expected_clear_nonce`.** A nonce-less or non-matching pass leaves the pending question standing so a later match can still answer; only `tap clear` itself consumes the question after it has observed verification or declared timeout/abandon. A non-matching `TAP_CLEAR_ID` writes nothing to the authority fields and emits a breadcrumb naming both nonces: a non-matching TAP_CLEAR_ID is not an answer to this clear's pending question.

**The identity twin diverges here, deliberately, and the divergence is the same rule (tap-zqcd).** `identity_capture`'s `expected_harness_session_id` is the same shape of pending question, and it follows the same principle — *the party that asks retires its own question* — to a **different mechanism**, because the asker is not the same kind of thing. `tap clear` is still running and watching while its nonce is outstanding, so it can retire its own question on timeout or abandon. The launcher exits at `mark_launch_ready`, and the registration it was asking about can be refused afterwards, in a different process, minutes later. With nobody left to retire anything, the retirement becomes an **operator act**: `tap register <h> --accept-observed-identity` (§tap register flags), scoped to the launcher's question alone. Retirement by ANSWER or SUPERSESSION otherwise — registration pops the expectation only on the accept branch, and a new launch's reservation replaces any prior unanswered one wholesale. Do not read the two fields as inconsistent: same rule, different mechanism, because one asker is alive and the other is gone.

**The clearing fence (tap-36kb).** During the stamp→respawn→await window the registry row stays `status=active`, so deliverability alone would still inject into a pane mid-restart. `tap clear` therefore holds an exclusive flock on a per-seat marker whose CONTENT is the courier's signal: clear nonce, UTC stamp, awaiting pid, harness, and the family await ceiling. The flock serializes WRITERS only — a second concurrent clear fails `LOCK_NB` immediately, exits **2** having changed nothing, `error_class=clear_in_progress`, naming holder pid + since. The courier reads the file without taking that lock. A live marker (now inside the family ceiling) parks the send via the existing spool (`reason=clearing`); drain observes the same marker through pane readiness (`busy:clearing`) and does not inject until the marker is gone or expired — including against the spool busy-deadline, which must not force an inject while content still says live. `--urgent` (and `kind=escalate`, which defaults urgent) refuses with `error_class=recipient_clearing` — distinct from `clear_in_progress`. **This fence FAILS OPEN past the family await ceiling** — the courier treats a stale marker as expired, delivers anyway, and says so once per non-empty clear nonce. An empty nonce is not a suppression key, and an unwritable notice sidecar also fails open, so either condition warns on every observation rather than going silently stale. That polarity is opposite the self-clear guard, which fails CLOSED: a courier failing closed is a delivery outage for every seat, and the consumer's cost decides. Pid death is not the courier's signal; a dead clearer with a still-fresh stamp still parks, because the pane may be mid-restart. **`tap refresh` must not delegate to `tap clear` until this fence exists** — it does now.

**The nonce is an operational freshness stamp, not a credential.** It is a PUBLIC field: it sits readable on the row, and a deliberate re-register can present it. Its value comes from being minted per clear — a row carrying it was written by a registration that ran after this command started — never from being secret. It attests that *this* registration came from the process this clear started. TAP is not a security boundary (§Trust model), and nothing about this field should be hardened into authentication.

## Clear-fence location

An enrolled seat's clear fence lives at `<recipient-bus>/clear-fence/<handle>.json`. The bus belongs to the enrolled root, independently of the acting registry's location: `busHomeForEnrolled(root)` selects `.tap/bus`, then an existing `tmp/tap`, otherwise `.tap/bus`. Clear writes there; indexed remote send, spool readiness, and single/digest delivery read there. Readers remain lockless and use the marker's age and ceiling.

A spool entry with no `to_team` uses the current bus. For a qualified entry, a live machine index must bind `to_team` to the same realpath as `target_registry` before the reader uses the enrolled root. The acting registry's supplied `team.name` and `team.worktree_root` must also agree with that enrollment, using the selector's existing consistency check. An absent or invalid index holds with `unanchored_bus`. A historical, unreachable, malformed, or mismatched binding holds with `fence_authority_mismatch`; readiness reports `busy:decision-unavailable`, and no pane effect or attempt is admitted. The sender cancels or resends after repairing the binding.

A live index that positively lacks the named team permits the existing registry-derived manual bus. The entry's current binding decides this; no origin field is stored. A manual send parked against a different registry for an already-enrolled team now holds on mismatch.

Direct `--remote-registry` sends retain their file-pinned authority and do not sample the index. An enrolled clear fence at a root-relocated bus can therefore remain invisible to that direct manual door. Changing that limitation requires changing the manual door's contract; it is not a fallback when enrolled authority is unavailable.
