## Recorded launch workdir (2026-09-25)

From an enrolled team root, `tap session launch <preset|harness> [name] --workdir <path>` starts the harness in an existing checkout of the same Git repository. Relative paths resolve from the caller directory; symlinks resolve to the canonical checkout root. A missing path, checkout subdirectory, or unrelated repository refuses before enrollment or reservation. Dry run performs the same validation without writes.

The seat recipe records `launch_workdir` separately from its team anchor (`registered_from_worktree`). Launch, resume, restart, clear and relaunch use the recorded workdir for the harness process and revalidate repository membership before replacement. Relaunch does not infer a directory from an incidental shell `cd`. A missing or removed recorded checkout refuses rather than falling back to primary. Rows without `launch_workdir` retain their existing startup directory.

The explicit option does not enroll another team or change implicit worktree ownership. The existing pane registration remains on the launching team's bus. The relaunch census includes `launch_workdir` in its guarded identity: a recipe change after selection refuses before respawn. A launch collision that delegates to resume refuses a supplied `--workdir`, because resume replays the stored recipe.

Single-seat `--workdir <path>` repairs the recorded directory: [part 3](seat-relaunch-tap-session-relaunch-v0-22-part-03.md#repairing-a-seats-workdir-tap-p8xog).

```sh
# Run at the enrolled team root; Lane is already a linked worktree.
tap session launch astra lane --workdir ../Lane
tap session relaunch lane
```

## Seat relaunch (`tap session relaunch`) (v0.22)

`tap session relaunch <[team/]handle> [-m <instruction>] [--workdir <path>] [--dry-run]` **replaces a seat's harness process inside the pane it already occupies and RESUMES its stored conversation.** It is the sibling of `tap clear`, and the two differ in contract rather than mechanism: clear gives the same seat a **fresh** context, relaunch gives the same seat the **same** context. It exists because some harness credentials are read only at startup — a swapped account never reaches a running process — so a capped fleet must be restarted without losing what any seat was mid-turn.

**`-m` needs a delivery channel.** Opencode receives it over the bus after the rebind; hermes has none (its argv carries no prompt), so `-m` on a hermes seat refuses with `instruction_unsupported` before any effect, dry-run included. The member's result carries code 2 and that class; like any failed member it makes the aggregate exit 1. Relaunch without `-m`, then follow with `tap send <team/handle> -f <file>` (the refusal names the exact team-qualified recipient).

**The resumed child does not inherit the caller’s `TAP_HOME`.** Its command unsets that pin and starts at the recorded launch workdir (or legacy cwd); the existing pane binding retains the target team’s bus.

**Launch and relaunch children start without inherited harness identity.** The server's harness identity variables (`INHERITED_IDENTITY_ENV`, `TAP_SELF` included) are removed from every launched or resumed seat and crew child unless its invocation sets them; `TMUX`, `TMUX_PANE` and the bus and socket pins stay.

**It is not a second implementation.** Both verbs call one in-pane replacement transaction: the clearing fence, the `expected_clear_nonce` stamp, `remain-on-exit` armed before the respawn, `respawn-pane -k -c $HOME` whose command enters the recorded launch workdir (or cwd) before it execs (tap-p9v8: tmux can strand its server in a `-c` directory), and the exit surface. They deliberately use different completion witnesses. `tap clear` starts a new context and still requires the fresh process to answer the nonce through registration. Relaunch preserves the active seat row and exact pane, so after `respawn-pane` succeeds it waits until that same pane and tmux-server generation are alive, observably running the intended harness, and carrying a `#{pane_pid}` on the same tmux record that differs from the process that was replaced — same pane, same generation, alive, and intended command are all true of the old process, so they are not a completion witness on their own. A resumed conversation is not required to re-register merely to prove that the already-registered seat still exists. The replacement worker records its respawn and readiness details in the structured receipt; normal relaunch output stays quiet. The other differences remain the invocation (`resume` rather than `new`, so `harness_session_id` is kept rather than nulled and re-minted) and **the scrollback is deliberately NOT cleared** — the conversation survives, so the operator's local record of it survives with it.

**A bare single-seat handle selects the current enrolled team; `team/handle` selects an explicit team.** `<team/handle>` resolves through the global registry to that team's root and registry location; the bus is derived from the **target root's own authority** (`registry_v20.bus_home(root)` — `<root>/.tap/bus`; without that directory, a `<root>/tmp/tap/registry.json` entry refuses `old_store`, and a lookup error refuses rather than treating the old store as absent), and the reset-fence check, the clearing fence, the nonce stamp and the process-readiness wait are all taken against the target team — **including the post-acquire recheck that closes the clear-vs-reset race**, which must be given the same target bus. Left ambient it reopens exactly the window it exists to shut: the precheck fences the target, the target's reset publishes its fence, and the recheck inspects the *caller's* bus, passes, and lets the respawn run beside a live checkpoint. A source-order guard cannot catch that — it proves a recheck happens, not which bus it read. Recovery text in every refusal is likewise target-scoped, since `tap session restart`, `tap team` and `tap clear` are all caller-team-scoped and a bare copied command would act on a same-named seat in the caller's team. A cross-team verb that fenced the caller's own bus would mutate one team's registry under another team's guarantee, and the target's courier and reset would not observe the fence meant to stop them. **The bus comes from the ROOT, not from the registry file's path**, and the distinction is not cosmetic. Deriving it from the registry's location holds only while that location sits inside — or one level above — the bus. A **relocated** acting registry (`<root>/.tap/elsewhere/registry.json`) yields `<root>/.tap/elsewhere`, while the courier and the reset both observe `<root>/.tap/bus`: measured, not inferred. Every fence this verb takes would then be published and read where nothing looks, which is this section's own target-bus requirement failing one layer below where it is stated. The path-shaped helper remains correct for callers that hold nothing but a path; a caller holding the root asks the root. An unresolved current team refuses rather than widening; an explicit qualified key never falls back to the caller's team. Resolution reads **one** team, not the machine-wide walk `tap session list --machine` performs: that walk raises on the first unreadable registry anywhere on the machine, which would let an unrelated team's corruption veto a healthy seat's relaunch.

**The batch form: `tap session relaunch --harness <claude|codex|cursor|opencode|agy> [--team <t>|--team='*']`.** The families are **claude, codex, cursor, opencode, and agy** (opencode **2026-09-17**, agy **2026-11-22**); the single-seat form stays generic, while the fleet form selects and respawns a cohort and is limited to ruled-on families rather than every harness the launcher knows. `hermes` remains outside this allowlist. With no `--team`, it selects the **current enrolled team**. A named team selects that team, and `--team='*'` explicitly widens to every enrolled team. An empty or whitespace-only value refuses (**2**) rather than widening. Candidates are **active seats only**, using the same live-pane/current-server classifier as `tap team`. Offline, suspended, gone, unknown and poll rows are excluded before replacement; an active crew row is a candidate replaced fresh in its own pane (part 02); inactive rows belong to `tap session resume` / `tap team up`. Selected seats run concurrently under their existing per-seat fences. A positional seat and `--harness` are mutually exclusive and one is required. Machine-wide account recovery callers use `--team='*'` explicitly.

**A seat that changed since enumeration is refused, not respawned.** Scheduling and process startup can separate the moment a row is classified from the moment its worker reaches the effect, and the worker re-reads the registry. The enumerated row's identity — harness, pane id, and stored conversation id — therefore travels with the key, and the turn refuses that seat if any of the three has moved, failing that candidate (aggregate **1**) without replacing anything. Harness alone is insufficient: a seat replaced by a different seat on the same harness has a different pane and a different conversation, and this verb promises the SAME conversation. **The stamp and effect checks are separate bounded steps.** Under the clearing fence, Bun takes reset custody and the registry lock, reads the row again, checks the enumerated identity and effective resume target, and stamps its nonce and resulting launch recipe. It releases both durable-write locks before pane I/O. Immediately before respawn it observes the pane and re-reads the registry without a lock, requiring the same pane, server epoch and boot, its own `expected_clear_nonce`, and the enumerated identity and effective conversation. Drift at this check consumes only this replacement's nonce and refuses without respawn. No tmux call or readiness wait holds reset custody or a registry lock. The clearing fence spans the whole operation; a reset sees that claim and refuses `clear_in_flight`.

**The identity compared at that boundary includes the EFFECTIVE conversation, not the stored field.** The resume target resolves through a chain — the acting `harness_session_id`, then an id derived from `transcript_path`, then a quarantined id — so for claude the conversation a resume would actually enter can change while the row's own bytes do not; a transcript file appearing on disk is enough. The effective id is therefore resolved once at enumeration and compared before argv construction, under the stamp lock, and again before respawn, because one comparison cannot carry the promise alone. The seat's turn resolves the effective id again and refuses on any difference **before argv exists**; the enumerated value — not that resolve — is then what the invocation is built from. The boundary repeats the comparison against its own fresh read under the held lock, covering drift that arrives after argv was rendered. One compare on its own leaves a hole: the boundary alone cannot see a value that appeared and then went back, since disk may resolve `new-id` for the argv build and return to `ghost-id` before the locked read, leaving the boundary approving the enumerated id while the built invocation carries the other one — two agreeing resolves at different instants are not the same fact. The pre-argv compare alone would in turn miss a change arriving after it. Together they make the value that authorizes the value that runs. A different effective id, including a transition from none to some, refuses before replacement; a failed late check retires only its own nonce — the dry-run render is downstream of the first compare, so an unauthorized conversation is never even displayed.
