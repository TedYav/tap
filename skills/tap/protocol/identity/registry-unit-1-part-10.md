- Incumbent is an **active poll-mode member** and the newcomer's handle was **derived** → occupied by declaration (a daemon's seat has no pane to probe) → **auto-suffix**; a bare register never silently rebinds a daemon's handle. An **explicit** name is the instruction that authorizes the documented poll→pane seat conversion (delivery reset, `wake_url` dropped — §Poll-mode delivery class), and the poll write path itself remains a plain explicit-handle upsert.
- Incumbent is `status: pending` with a live reserved session or still inside grace → only the reserved session may complete the claim; a different session gets `error_class=seat_pending` and the row stays pending. Once the reserved session is gone and the grace has elapsed, the pending row is expired: refresh trims it and bare launcher allocation/claim may reuse the handle. `--force` is the explicit override for an operator-authorized rebind.
- Incumbent's identity AND address are **both gone** → a true corpse; reclaim the exact handle (the ordinary re-register-after-restart case).
- Incumbent is the **same pane** (same `pane_id`) → re-register in place.
- Incumbent's identity (stored `pane_id`) is **dead** but its address still hosts a live pane in the SAME tmux session → our own agent restarted in a new pane (harness restart recycled the pane identity); reclaim the exact handle, no suffix. Session is compared via `tmux display-message -t <pane> '#{session_name}'`. A live incumbent whose IDENTITY is still alive is NOT a restart — it is a same-session sibling (e.g. a crew pane) that must auto-suffix, never capture the incumbent's handle (tap-xat9: the SessionStart hook's bare auto-register used to derive the driver's handle from the shared session name and steal the live incumbent's seat).
- Incumbent is a **live pane in a DIFFERENT session** (directly, or via the recycled-address probe) → **auto-suffix** to the next free `<handle>-N`; never clobber. Registration never takes a handle whose recorded pane address hosts a live pane it does not own — attached or not. A live registered pane is reported as such; when the registered pane is gone but its address has recycled to a different live pane, the warning reports those two observed facts and directs the operator to `tap team` before naming `--force` as a conditional reclaim. `--force` is the only override and reclaims the exact handle instead of suffixing.

**GONE naming is shared with session-name allocation.** A pane-backed current row is observed GONE only when its stored pane identity and recorded address are both absent. Pending reservations and poll rows hold their name by declaration. A GONE row still owns its handle and therefore reaches the launch collision chooser; it is never silently treated as off-roster. Refresh may explicitly delete it, after which a later launch is fresh and no archived history becomes current authority.

**Allocator proposes, ladder decides — the asymmetry is deliberate.** The allocator's absent-seat predicate is **advisory, for naming only**; `tap register`'s ladder re-probes under the registry flock at claim time and remains the **authority**. The allocator is deliberately **more conservative** than the ladder: it frees a name only when the seat is certainly gone, while the ladder may reclaim more aggressively under its lock — a **suspended row with a live pane** is the named case (the ladder reclaims it; the allocator does not free it). That is the only safe direction for the two to disagree, because **the allocator must never propose a name the ladder would refuse**: a conservative allocator costs at most one suffix, while an aggressive one could hand out a live pane's name. A seat that returns between naming and claim collides into the ensure ladder, which is correct behavior rather than a race to defend against at allocation time.

**Occupied panes never change identity by accident (tap-5jc6):** an **explicitly named** register whose pane already holds an active row for a DIFFERENT handle is refused **before anything is written** — `error_class=pane_occupied`, exit 1, registry untouched, the caller still holds its own handle and its own mail. The refusal names `tap out` then `tap in <name>` as its action, because a caller the refusal has just proven holds a handle can always run it, and its detail names `tap session restart <name>` for bringing a launcher-managed seat back in a pane of its own — the recovery the caller actually wanted. The guard keys on the ABSENCE of a row for the REQUESTED handle on this pane, never on the presence of some other row, so case (a) residue cleanup below is untouched: a pane holding both `seat` and a leftover `seat-2` still sweeps the leftover when it re-registers as `seat`. A **derived** handle is the pane's own session naming itself (a rename, a relaunch), not an operator naming someone else's seat, and is not a rebind request; `--force` is the explicit one-step rebind and keeps the documented fork reclaim (`tap in seat --force`) working. **Named limitation:** the derived exit is REACHABLE, and is deliberately left open. A bare `tap register` in a pane whose tmux session has been renamed to another seat's name derives that name and rebinds without refusing — the shape `tmux rename-session` creates, which is step 2 of the documented tap-rxqb recovery. It is left open because the derived path is how a pane re-registers itself after a rename or relaunch, and refusing it would break that recovery; and it is a weaker trap than the specimen, because a rename is a deliberate act aimed at this pane rather than a one-word recovery command aimed at another seat. Closing it needs a way to tell "my session was renamed" from "I am now standing in for someone else", which this rule does not have. Where a rebind does proceed, the released row is announced as what it is — `tap register: identity rebind: this pane gave up '<h>' to become '<name>'` — instead of the stale-handle wording, which stays for genuine residue; the `__tap_register_released=` control record is unchanged in both shapes. The failure behind this rule: with a driver's pane gone, a leader ran `tap in <driver>` from its own pane, the dedup below released the leader's live handle as "stale", and the only tell was one success-shaped line — after which the leader wore the driver's identity and the independent final gate quietly became self-review. That error does not surface as an error; it surfaces as an approval.

**Seat dedup:** one *pane* owns one handle, and a relaunched seat reclaims the DEAD handle it held before the restart. After the write, an OTHER active pane-backed entry is released when it is either **(a)** our exact pane (`pane_id` match → `released stale handle '<h>' (same pane)`; residue from a prior handle this pane held — a `claude-seat`→`seat` tag migration, or a lingering `seat-2`), or **(b)** a **corpse in our tmux session** (→ `... (same session)`): its recorded `pane_id` no longer resolves AND the seat is ours — its old address now hosts our new pane, or the address's session segment equals ours. Case (b) is the relaunch-under-a-new-handle reclaim (tap-e9h): a cleared/restarted session mints a fresh `pane_id`, so the strict same-pane match misses the stale handle and it would otherwise stay silently addressable. A **live** incumbent pane with a *different* `pane_id` is never released — it is a genuine other seat, including a pane-crew sibling in our own session (one SESSION may host several live seats; the rule is one-pane-one-seat, never one-session-one-seat). Poll seats have no pane and never collide here.

**Selected-team recipient recovery (tap-mxf95).** A payload found on another bus does not change the caller's selected team. When an instance-bound read or reply cannot resolve the actor instance in that selected registry (missing row, empty instance, or unreadable data), it refuses as `instance_unresolved` and directs the caller to retry from the registered team's checkout or with `--team <registered-team>`. Existing exact adoption grants are evaluated before this refusal, and `read --force` cannot override it. An explicit `TAP_HOME` must be checked before relying on `--team` recovery. It must not describe an absent row as a replaced instance or suggest sender cancellation. A present row with a different instance retains the existing refusal and recovery; selector precedence, adoption grants, and settlement ordering are unchanged.

**Init ordering and refusal.** `tap init` retains the create-or-validate, canonical-bus fold, then enroll sequence. Under the acting sidecar lock, an existing acting file must parse as a team registry (schema `0.20` or `0.21`) with team and seats objects; otherwise init refuses to fold or enroll over it. A missing file is created fresh, and a valid existing store remains unchanged.
