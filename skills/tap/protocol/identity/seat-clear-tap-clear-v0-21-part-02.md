**Per-harness instruction channel.** claude, codex and cursor take `-m` as the fresh process's **initial argv** (positional), so no keystroke is simulated. **agy requires `--prompt-interactive`** — its `--prompt`/`-p` is an alias for `--print`, which would run one prompt non-interactively and exit, turning a restart into a stopped seat. **opencode has no interactive initial-prompt argv** (the positional is a project directory; `opencode run` is non-interactive and exits). A bare `tap clear <opencode-seat>` already works and parks. With `-m`, the instruction rides a settle-only bus send after the rebind is verified, placed while the clear fence is still held so drain delivers it before any send parked later in the window (tap-0jtk, consuming the tap-thgv send rail). The send passes `--from $TAP_SELF` when that identity is set, so a pane-less poll seat can deliver; without `TAP_SELF` and without a pane identity, send refuses `unregistered`. **A failed send after verified rebind exits 6, not 0** — the seat is already restarted, the requested instruction is not on the bus, and reporting success is how a caller holds a receipt for a delivery that did not happen (same polarity as `tap compact`'s dropped-focus arm). stderr names `tap send <handle> -f <file> --fyi --wake --from <your-handle>` (or the resolved `TAP_SELF`); outside tmux, `--from` selects an already active sender. A pane-less caller without one must first register a stable poll seat on the intended team, then send; pass `--team` when the working directory does not identify that team. A pane-backed caller registers from its pane instead. `--wake` remains a compatible note spelling. All new notes require recipient read; arrival follows the composer policy. Mail parked earlier in the clearing window may drain ahead of the instruction; the pin is later-parked mail, not "first work". hermes is out of scope as goalie infrastructure rather than a conversational seat.

**Refusals, each naming its recovery path.** A seat whose registered pane is gone is refused — clear replaces a live process, and with none there the operator needs the relaunch path (`tap session restart <seat>`) instead. Pane ids captured under a **prior tmux server generation** are treated as absent, never dereferenced, since a recycled id names an unrelated pane. **The two ownership guards have deliberately opposite polarities.** Occupancy fails OPEN — an unreadable session name warns and proceeds, because refusing every clear whose probe hiccups would break the verb for an operator with a working seat. Self-clear fails CLOSED — an unprovable caller pane refuses, because the state it guards (the command ending its own process mid-transaction) cannot be fixed by trying again. **A recycled pane id is refused**: the pane must live in the session the seat is on record as occupying, because a registry row can outlive its seat and existence alone would authorize replacing a stranger's process. **Self-clear is refused**, and the caller's pane is resolved from its controlling tty. `TMUX_PANE` is **not consulted at all, not even as a fallback**: an inherited or stale value that merely differs from the target would otherwise walk a self-clear past the guard, and — worse — when the tty walk cannot answer, a truthy stale value would ALSO suppress the unprovable-caller refusal, handing the decision to the untrusted source the walk exists to replace. An unresolvable caller is treated as unprovable, never as elsewhere. Inside tmux with no resolvable caller pane the verb refuses rather than assume it is elsewhere; a caller outside tmux entirely is provably not the target and stays allowed: the command would end its own process before it could verify the rebind, leaving the seat to come back mid-transaction with nobody watching, so a seat clears itself by asking someone else to.

**Same verb for hung-harness recovery, no discriminator flag.** A hung harness is the identical operation with a more abrupt stop, and a separate verb (or a `--force`-style flag) would only ask the operator to diagnose before acting.

**Exit codes.** **0** cleared and rebind verified (and, on opencode with `-m`, the instruction send landed). **2** REFUSED, having changed nothing — unsupported harness, pane gone, self-clear, unknown seat, **or `clear_in_progress`**. **6** cleared and rebound, but the opencode `-m` instruction did not land: the seat is live; do not retry the clear; send the instruction with an explicit `--from` naming an already active sender. **7** respawned but the rebind was NOT verified within the timeout: the process has already been replaced, so this is not a refusal and must not be retried as one; the process may still be starting or may have failed to launch, and the pane is the authority. The 2/7 split is the same distinction `tap refresh` draws with its own 7 (§Seat refresh) — a destructive half that succeeded while the completion did not gets a code of its own, because what the operator does next differs. `--dry-run` prints the composed launch command and changes nothing; on opencode with `-m` it also notes that the instruction rides tap send after rebind. **A respawn that fails outright** — `tmux respawn-pane` itself erroring, most plausibly when the pane disappears between the liveness check and the respawn — exits with **tmux's own code**, and the expectation stamp has already been written; the seat is untouched, and re-running the verb is safe.

**Relationship to `tap refresh` — policy over one engine, and why the split existed (tap-utpn).** Both clear a seat's context. `tap refresh` is the **policy** layer (obligation-boundary guards, `--fresh` instance retirement, the ordering invariant, its own exit surface) and **delegates its clearing to `tap clear`**; `tap clear` stays directly reachable for the no-policy stuck-harness case. **The history is load-bearing and is kept deliberately rather than trimmed as resolved.** Refresh's engine used to be `tap command clear` — an *injection* clear: verified-submit into the live process, then re-registration by the clearing command itself. The swap waited on two things, and knowing which is the difference between reading this as caution and reading it as design. First, **the courier clearing fence** (above): without it a send could race the respawn window, so refresh delegating to clear would have made every refresh a delivery hazard. Second, **the exit-code surface**: a respawn that never re-registers is a different partial state from a submit that did not complete, and the arms had to be re-verified against a mechanism whose failures differ — which is where refresh's translation of the engine's 7 comes from (§Seat refresh). Two consequences of the old engine also retired with it rather than being ported: it re-registered the seat itself, so it needed a pre-reset check that the row's `reply_to` was still deliverable — `tap clear` never re-registers (the fresh process does), so that guard has no analogue; and its injected recovery prompt is replaced by the rebind recap `tap in` already prints.

**Why the direct `tap clear` path needs none of refresh's guards.** It does **not** retire the instance. Obligations bind to `(handle, instance)` (§Seat refresh), so they survive a clear and remain settleable by the same seat, and the fresh process's `tap in` delivers the rebind recap that re-points it at them. This is the reason clear is safe without an obligation gate — recorded because it is not reconstructable from the code, and because wrapping clear in policy "to be safe" would duplicate the layer tap-utpn exists to unify.
