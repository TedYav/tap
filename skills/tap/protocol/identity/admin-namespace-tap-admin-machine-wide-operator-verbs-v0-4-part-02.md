For each enrolled team whose bus/registry is readable, refresh runs the shared exact-session classifier over every pane-backed seat and **deletes only rows observed `gone`**: tmux supplied a readable current-generation session snapshot and the exact stored session name was absent. A recycled pane id in another session cannot keep the row alive; designated-pane disagreement, an exited harness, stale boot/server provenance, or unobservable evidence yields `offline`/`unknown` and is preserved. Poll-mode seats are never touched. It then classifies teams (`active` / `dormant` / `dangling` / `unreadable`, same rules as `dashboard`).

**Accumulator semantics (data-gone purge, tap-25p).** Refresh **PURGES** an index row — with a loud `PURGED '<team>' from index (...)` receipt — for each team whose data is definitively gone: a **`dangling`** root (the worktree directory no longer exists → reason `root_gone`), or an **`unreadable` team whose indexed `registry_location` is positively observed missing** (a `FileNotFoundError` on the stored acting path, under live v0.20 authority → reason `registry_missing`). A legacy bus decoy (`<root>/.tap/bus/registry.json`) never stands in for the missing acting store, so a team whose acting store is gone is purged even when a decoy would read as healthy. A present-but-**corrupt** registry is a deliberate exception: it is **never** purged — auto-purging present-but-broken data would destroy the evidence a human needs — so it stays in `cannot_check[]`, untouched, and still forces exit `1`. The same protection covers a registry that is present but unreadable or unprobeable: a purged row requires the positively observed missing store, never an inability to inspect. A **`dormant`** team (live root + readable registry, only its panes are dead) is **not** purged either: it stays a **`retire_candidate`**, blocked only by current poll-mode members, and `tap admin retire` remains the ONLY removal path for a live team; `tap team shutdown` de-enrolls a **stopped** team — one whose acting registry is already observably gone — as part of its own lifecycle, so retire's exclusivity holds precisely while the team is still live. Purged teams are gone, so they are never also emitted as retire candidates. The index write reuses `retire`'s native writer: `teams.json.lock`, then `global-registry.json.lock`, with the live marker rechecked under each, and an atomic replace. The guarded `registry_missing` purge first takes the acting registry's sidecar lock and writes a capture artifact before it publishes the removal. `tap teams refresh` aliases the public `tap admin refresh`; arguments and receipts are identical.

**Reversibility (index-purge snapshot, tap-k140).** Before a real run purges any index row, refresh writes an exact snapshot of `global-registry.json` beside it (under `recovery/`, named `index-admin-refresh.<hex>.json`) with a sha256 sidecar, and prints one stderr line naming the snapshot, the digest and the restore command (`cp '<snapshot>' '<index>'`). The snapshot survives the run as the restore point. Restoring replaces the whole index, including enrollments made after the snapshot was taken — teams enrolled in between must be re-enrolled by hand. A snapshot that cannot be written purges nothing (a warning names the refusal, no purge is reported, and the index stays intact). `--dry-run` still writes nothing and prints nothing beyond its ordinary report.

**Fail-closed per team:** a team whose registry is present but cannot be read or probed — or whose indexed `registry_location` cannot be inspected (unprobeable path, malformed index entry, helper failure) — is reported in `cannot_check[]`, left untouched, and other teams still process. A whole-sweep failure (the machine index itself is malformed/unreadable) is the ordinary structured `registry_invalid` failure — no mutations, no fabricated report shape (same two exit-1 shapes as `dashboard`).

**Exit codes:** `0` when every readable team processed cleanly (purging data-gone teams is normal, successful work and never forces `1`) · `1` when any team is in `cannot_check[]` (present-but-corrupt registry; the cannot-check bias outranks "nothing to do") — same rule as `dashboard`.

Every seat deletion and every index purge prints one line; `--dry-run` prints byte-identical lines (including what it WOULD purge) with zero registry **and** zero index writes. `--json` emits `{ok: true, dry_run, trimmed: [{team, handle, pane, reason}], purged: [{team, reason}], retire_candidates: [{team, classification, blocked_by, recommended}], cannot_check: [team, ...]}` (`reason` ∈ `root_gone`·`registry_missing`). Seat deletions append registry-event audit lines on each team's bus.

The hermes cron runs `dashboard` (read-only); a human or judge runs `refresh` when they want dead seats trimmed and retire candidates named.

### `tap admin rebuild-registry [--yes] [--json]`

The machine-wide **additive recovery** operation. It scans every pane under each enrolled team root, accepts only a known TAP harness, derives the same team-local handle `tap register` would, and forms a per-seat plan. Bare invocation is the dry-run report; only `--yes` applies it. Applying takes the registry's sidecar lock, re-reads it under that lock, then atomically updates the observed harness, pane target/id/current command and server generation for each recovered handle. Existing rows retain `delivery`, `status`, `status_reason` and `registered_at` exactly, including absent keys. Trust, identity-capture, quarantine, launch/session, poll settings and unknown fields remain untouched. The existing worktree binding and instance are kept; a missing binding or instance is initialized as before. Only new or null rows receive pane-delivery, active-status and registration-time defaults. A pane sweep cannot attest a registration choice or undo a parked state.

This is intentionally not `refresh` in reverse. A live pane attests only itself: rebuild **never deletes** a row it cannot observe. Poll members, dead-pane rows, and other existing provenance survive unchanged. A recovered pane with the same handle as an existing row overwrites that row's pane-derived truth. When same-session panes derive one base handle, a row whose stable `pane_id` matches a live pane retains its registered handle; other live siblings receive deterministic `-2`, `-3`, … suffixes rather than blocking recovery. With no matching row, the stable pane-id order chooses the base handle and suffixes its siblings. A missing registry refuses (run `tap init`); a malformed existing registry is fail-closed and left intact. Use `tap admin refresh` / `tap team refresh` for deliberate zombie removal, never rebuild.

`--json` emits `{ok, dry_run, planned, applied}` on full success. `planned` is every pane-derived `{team, handle, pane, pane_id, harness}` row; `applied` is empty for the bare preview and contains the rows atomically upserted by `--yes`. When an observed pane belongs to a stored poll or suspended row, an optional `preserved` array reports `{team, handle, pane}` plus the stored string values of `delivery`, `status` and `status_reason`. Human output names the same retained decisions. Preview reports its snapshot without writing; apply reports the fresh locked row. A successful rebuild can therefore leave a seat suspended or in poll mode; re-registration remains the explicit way to change those decisions.

**Partial-refusal when enrolled acting authority is unreachable/invalid (WAVE 6.5 / C6):** skipping an enrolled team under a live or invalid flip (so rebuild never writes the bus decoy) is not ratified as partial success. The command still may upsert other teams' observable panes, but the receipt is one JSON document with `ok: false`, `skipped: [<team>, ...]`, `skipped_reason: "acting_registry_unreachable_or_invalid"`, plus the usual `dry_run`/`planned`/`applied` fields, and exit `1`. Human mode names each skipped team on stderr and then emits the ordinary structured failure. Under `--json` there is **no** second error-object document after the amended receipt (exit `1` alone).

### `tap admin migrate-registry` (removed)

TAP never converts old registry formats. For one release the verb stays as a stub: any invocation exits `1` with `error_class=old_store`, detail `tap admin migrate-registry was removed; this TAP reads only {"schema":"0.20","team":{...},"seats":{...}} team registries and never converts old files`, and action `ask an agent to upgrade an old team registry by hand (rename "agents" to "seats", add "schema": "0.20"); move an old teams.json or launcher sessions.json aside; then run tap init`. `--json` selects the JSON error object. `tap init` and `tap doctor` only detect an old `teams.json`; they name it and say to move it aside, then run `tap init` in each team root.

### Reset archive lifecycle

Team reset archives are durable recovery backups: every `tap team reset` preserves one exact archive, and no reset invocation deletes an earlier archive. `tap team restore` puts a COMPLETE checkpoint back; `tap team purge` is the only deletion path and takes one exact archive name, previews under `--dry-run`, prompts on a TTY, and refuses non-interactively without `--yes`. Reset archives, restore recovers, purge deletes, rebuild re-derives observable live pane seats, and refresh reconciles current rows.
