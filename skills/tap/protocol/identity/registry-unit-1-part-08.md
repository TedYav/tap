OpenCode resumes a captured conversation with `--session <harness_session_id>`. The invocation builder is the only source of that flag: after persisted passthrough and live `[harness.opencode.params]` compose, the final argv policy removes every external `--session`/`-s` and `--continue`/`-c` spelling, including equals forms, then appends only the record-owned id. TAP never passes `--continue`, because a shared cwd cannot identify which seat owns the latest conversation. An id-less row prepares a fresh native session; a preparation fallback emits one stderr notice and does not abort `resume --all` or `tap team up`. A fallback reservation uses `mode=launcher_new` so the plugin's first capture becomes trusted; a captured or prepared resume id uses `mode=exact_resume` with that id as the expectation. The stopped-seat picker uses the ordinary resume option, described as exact when the row has an id and fresh when it does not (tap-ql59z, tap-kq65d). A captured id that OpenCode's store provably lacks refuses resume ([native-store evidence](resume-store.md), tap-dt6kf).


The intermittent submit-dead failure attributed to `--session` was a terminal-mode race in the OpenCode plugin's init-time bind. Its `tap in` child inherited the pane tty on stdin; `bin/tap` execed system Bun 1.3.8, which snapshot cooked termios at startup and restored that snapshot when the delayed child exited after the TUI had entered raw mode. Feeding the bind child through `< /dev/null` leaves Bun no tty to restore. oven-sh/bun#29592 changed the pipeline case in Bun 1.3.14, but the plugin rule is version-independent: every Bun child it starts during TUI boot must use `< /dev/null` so it cannot inherit the pane tty (tap-kq65d).

**OpenCode 2 session-start context:** TAP requires OpenCode 2.x. The server plugins use stable default definitions with `id` and `setup`. The shell supplies `OPENCODE_SESSION_ID` natively; the old session-env plugin is retired. Private mode remains the default and uses `--standalone`; only its `serve --stdio` child may bind through the plugin. The experimental shared-service mode uses launcher-owned activation and native shell/process evidence. Its plugin never registers a seat. See [shared OpenCode](opencode-shared.md) for opt-in, identity, stop and upgrade contracts (tap-ris29).

The launcher validates a requested model and variant through the native API, creates the session in the target directory, and opens `--session <id>`. Preparation is stateless to TAP and bounded to 20 seconds; requested tuning refuses on failure. An untuned launch can fall back to an id-less TUI with an explicit notice. Native resumes preserve their model and variant. Crew preparation runs only at the launch effect, after read-only validation; dry runs create no native session.

After binding, the private plugin reads `session-start.ts context-private <session> <root>`. The launcher recognizes this launch's bind by its token, exact prepared session ID and changed post-placeholder fingerprint, then activates the row after the survival settle. The read-only context producer waits up to four seconds for that active row, matching the launch witness, native session and live pane/session/generation. Timeout or rollback emits no context and never promotes a row. Native `session.synthetic` with `resume:false` and `delivery:steer` admits the result before the prepared session's first request (wire-proven on 2.1.2); it cannot start an idle turn or supply title input. Bare TUI-created sessions and late binds retain later-step delivery. Producer discovery remains override, sibling shim, then resolver-derived entry; children have no tty and a five-second bound.

Durable plugin storage, keyed by session ID, tracks the last context and parked-hint texts separately. Only changed text is admitted; a drained hint does not restack identity. Compaction and server restart retain dedupe. A deterministic synthetic ID makes an admission followed by a failed storage write safe to retry. Failed storage reads admit nothing. No session metadata is rewritten. Skills remain native OpenCode discovery.

**Poll-entry shape (explicit):** a `delivery: poll` entry carries `delivery`, `status`, `status_reason`, `registered_at`, `registered_from_worktree`, `harness` (free-form label, e.g. `hermes-gateway`), and optionally `wake_url` / `unattended`; it **omits** `pane`, `pane_id`, `pane_current_command`, `cost_mode`, and `include_policy` (no seat to include in reviews). Consumers must treat the pane fields as absent-by-design on poll entries, not as legacy damage; `tap doctor` does not warn on them. `wake_url` is valid on poll entries only.

**Status lifecycle:** Only a ready row whose current observation derives `active` is a pane-delivery target. The observation states are `active`, `unbound`, `gone`, `offline`, and `unknown`: `unbound` is a `suspended:server_restarted` row whose stored boot and server generation still match and whose exact session contains exactly one positively matching live harness pane, but whose invalidated pane binding has not yet been restored; `gone` requires positive absence of the exact name on an otherwise readable current-generation tmux snapshot; `offline` is recoverable provenance invalidated by a prior boot/generation or a positively observed exited harness; `unknown` covers unreachable/malformed tmux evidence, boot observation failure, designated-pane disagreement, harness mismatch or unattested expectation, or unsupported/failed harness observation. Observation failure never proves absence or exit. Like every non-`active` result, `unbound` blocks pane delivery. Membership-carrying verbs are `tap register`/`tap in`, real `tap session launch|resume|restart`, and explicit `tap admin rebuild-registry --yes`; resume and restart require an existing relaunchable current row. Reconciliation verbs (`tap session repair`, `tap team refresh`, `tap admin refresh`) never create membership. Launcher membership is a token-guarded transaction: `pending` reserves a handle; the created pane binds that token as active/launching; ready clears the reason and token; failure rolls back only the matching token. Pending and launching rows are non-routable. Reservation expiry is probe-based after grace and trims only when the reserved session is gone. A positively known epoch/boot mismatch makes the row offline immediately at every reader; there is no dispatch-time rewrite, including before `cancel`, `compact`, `clear` or a session adapter, so the row keeps its stored fields and an `active` row stays a relaunchable resume member. An ambient generation override cannot trigger a startup rewrite. Use `tap session repair <handle>` for a launcher-managed binding or `tap in` from the current pane to re-attest it; SessionStart also uses the registration boundary. Those explicit writers retain their own authority checks. Bare `tap team refresh` runs one observation/reconcile pass: observed `unbound` durable rows re-bind through the existing `tap register` writer after trim-lock work completes; missing, ambiguous, mismatched, explicitly retired, and otherwise relaunchable durable rows remain unchanged; observed `gone` rows and ephemeral crew residue are collected. Rebind failures leave the row unbound. `--dry-run` reports rebind-ready without writing. The earlier `--hard` parked-row branch remains authoritative and does not opportunistically rebind a live parked row. `suspended` rows block send until explicitly reactivated, except that `server_restarted` remains a relaunchable resume state. `user_removed` preserves a parked row, `session_stopped` supports team up, and unregister deletes the row and current resume authority.

**Pane-id write boundary and damaged-row recovery:** a persisted tmux pane identity is exactly `%` followed by decimal digits. Every pane-observing registry writer refuses malformed non-empty output as `identity_unverified` before mutation: targeted `tap register` observations, the launcher's bind/ready gate, native session repair, and `tap admin rebuild-registry`'s batched observation parser. Rebuild refuses the whole plan before apply rather than silently skipping one malformed pane. A pre-existing malformed `pane_id` classifies as `unknown`/unobservable, never `gone` or recycled; `tap send` refuses it before pane liveness, payload placement, effects, or suspension and leaves the row unchanged. A launcher-managed row is repaired from its exact live session by `tap session repair <handle>`; a manual row may be deliberately removed with `tap out <handle>` (without `--kill`) and re-attested from its pane with `tap in <handle>`.

**Retained panes:** tmux may omit `pane_pid` after exit. A record with `pane_dead=1` still carries pane identity for cleanup, never a running harness. Live-pane observations require a numeric PID; physical vessel identity is server/session/window/pane/socket, independent of PID.

**Session repair custody:** repair holds the literal registry sidecar lock while it rereads the selected row, observes panes and publishes a binding. The selected `instance`, `session` and `harness` must still match the locked row, including an instance that appeared while repair waited. A changed identity refuses with `session_error` (exit 2) and requires reselection. Missing rows, pending-session mismatches and user-removed rows keep their existing results; unrelated metadata and allowed status changes survive the locked reread.

Repair reads pane facts and their server epoch from one tmux record. A failed, timed-out or malformed live-pane observation refuses without changing the registry; it cannot authorize repointing. A positively missing target, a malformed stored pane identifier or a positively obsolete server epoch may lead to exact-session recovery. These rules belong to native session repair; shared Python resume, restart and clear observation behavior is unchanged.

**Teams and recipient identity:** the team is the git worktree or folder — the bus is scoped there, so all registered agents in one tree/folder form one team, recorded as `team.name` (basename) in the `team` block. Handles are unique _within_ a team, not globally. Unqualified send targets (`tap send codex ...`) are team-local; team-qualified targets (`tap send <team>/<handle> ...`) opt into cross-worktree relay when `<team>` differs from the local `team.name`. Git worktree top levels enroll in the machine-wide team index, and so does a non-git directory whose owner consented through `tap init` or a first `tap session launch`. A pane-backed recipient is the registry-bound **team + handle + exact session name + designated-pane membership**, never a handle, address, or stored pane id alone. Address resolution binds the target team and its exact registry before any recipient lookup. A readable `list-sessions` snapshot distinguishes exact-name `alive` from `observed_absent`; any failed or malformed snapshot is `unobservable`, never absence. A name-alive session is only session-scoped evidence: `list-panes -s -t "=<exact-name>"` must re-derive the row's designated address/id in the same server generation, and the expected harness must be positively observed there. A stale id that is live in another session, an address rebound to another id, or a gone crew pane inside a still-live driver session is non-active. Registry-resolved courier delivery re-runs this authorizer before canonical placement, before copy-mode cancellation (the first pane write), before clear/inject, and before primary/secondary Enter; drift stops further pane effects and leaves canonical/spooled bytes recoverable.
