## Admin namespace (`tap admin` — machine-wide operator verbs) (v0.4)

**Placement rule (the namespace contract).** Lifecycle and local health verbs are **team-scoped**, anchored by cwd/pane or an explicit supported selector; read/show resolution, team discovery, and context census have the documented cross-team read surfaces. `tap admin <verb>` verbs are **machine-wide**: they operate on the **marker-selected machine index** — `~/.tap/teams.json` pre-flip, `~/.tap/global-registry.json` post-flip (`TAP_INDEX_HOME` test override) — and reach across every enrolled team. An admin verb never anchors by cwd — it behaves identically from any directory (a cron's cwd is meaningless). Future verbs are placed by this rule, not by taste: `doctor`/`health` stay top-level because they are team-scoped; machine-wide maintenance goes under `admin`, while the documented discovery and inspection exceptions remain top-level. Reset is team-scoped: `tap team reset` checkpoints and reinitializes that team's acting registry and bus, and bare `tap reset` is its compatibility tombstone.

### `tap admin ps [--json]`

Read-only machine-wide process view, independent of cwd. Select registered teams from the marker-selected machine index; historical entries are omitted. Unknown enrollment states, non-directory roots, non-regular or unreadable registries, conflicting enrollments and invalid identity fields produce incomplete diagnostics. Confirmed inactive seats are omitted; active, pending and unresolved active registrations remain visible, except daemon seats (`delivery=poll` or `harness=daemon`). Daemon seats are omitted from text and JSON before process scanning and produce no missing-process diagnostics or failure exit.

One OS process snapshot supplies harness PID, CPU percentage, RSS KiB, elapsed process age and process state. For a shell-owned pane, only its foreground process-group leader can supply the harness process. Metrics cover that process, including its runtime wrapper, not descendants. CPU percentage is the OS `ps` value, not an interval sample. Each tmux socket is observed independently of the caller's server epoch. Activity capture is accepted only if the server generation still matches. No process arguments or transcript contents appear in output.

Human columns are team, seat, harness, PID, CPU%AVG, MEMORY, elapsed, process state, TAP activity/lifecycle and reason. MEMORY uses batched macOS footprint: decimal MB below 1 GB, two-decimal GB at or above. Unavailable footprint uses RSS with a per-row REASON label; fallback keeps exit0. JSON retains `rss_kib`; `footprint_kib` is integer KiB or null. Unknown values use an em dash. JSON returns `{ok, resource_scope:"harness_process", seats, diagnostics}`; each seat carries `team`, `handle`, `harness`, `status`, `activity`, `pid`, `cpu_percent`, `rss_kib`, `footprint_kib`, `elapsed`, `process_state`, `reason`. Unavailable metrics are null. Exit0 means a complete observation, including an empty machine. Exit1 means invalid input, unreadable index or incomplete observation; partial rows remain. Partial JSON failures add `error_class:"observation_incomplete"` and `action`; plain failures retain rows on stdout and emit one cause-and-`next:` recovery line on stderr. `tap admin ps --help`, `-h` and `help` show the dedicated help page.

Status uses the roster's dot-plus-word palette. Human CPU/MEMORY cells at least25%/1GB qualify for bold-amber emphasis and an ASCII `*`; emphasize the top three qualifying values per column, including ties at the cutoff. Null metrics never qualify. Emit one explanatory footer only when a mark exists. Team/seat ordering remains unchanged. Color requires a TTY, absent `NO_COLOR`, and `TERM` other than `dumb`; uncolored human output retains marks, while JSON retains raw metrics and its existing schema. 

### `tap admin dashboard [--fast] [--json] [--full] [--verbose] [--stale-after <secs>]`

`tap admin dashboard --fast [--json]` (also `tap admin --fast`) is a read-only, machine-wide roster view. It lists only teams with at least one pane seat observed `active` by the shared seat-identity classifier. Teams with no observed-active pane seat are omitted; unavailable or corrupt registries and unknown seat observations remain explicit diagnostics. Poll rows with stored status `active` become `unknown` with reason `poll_liveness_unobservable`; they do not count as live pane seats.

Fast mode uses one shared machine snapshot and does not perform payload, context, transcript, or history scans. An incomplete snapshot remains unobservable rather than triggering per-session fallback probes. It accepts only `--json` alongside `--fast`; full-detail flags (`--full`, `--verbose`, `--stale-after`) and mutation options are incompatible. The default output groups familiar roster columns by team.

Fast JSON is exactly one stdout object `{ok, fast, teams, diagnostics}`, with `fast: true`. Each team contains `{name, root, active, seats}`; each seat contains `{handle, harness, preset, pane, status, reason, attached}`. Diagnostics contain `reason` and optional `team`, `handle`, and `detail`, and are also printed on stderr. Exit `0` means the observation completed with no diagnostics (`ok: true`); exit `1` means a machine index, team, or seat was unobservable or invalid, or the arguments were incompatible (`ok: false`). This fast report does not use the full dashboard's attention/exit-2 sweep contract below.

Without `--fast`, the dashboard is read-only, zero mutation — it reads the marker-selected machine index directly and **reports** dangling entries rather than exercising the index's prune-on-read; seat-trim mutations are `tap admin refresh`; index de-enrollment is `tap admin retire` — the only operator de-enroll for a **live** team, while a full `tap team shutdown` de-enrolls the stopped team's index entry as part of its own lifecycle (the acting registry is already gone by then). Dashboard, refresh, retire and `rebuild-registry` never read retired `teams.json`; with no marker they refuse `unanchored_bus` (next `tap init  OR  tap session launch`). `tap teams refresh` aliases the public `tap admin refresh`. Per enrolled team it computes the same observable state `tap health` reports team-locally (team seats × seat states × unsettled payloads), then aggregates machine-wide:

- **Team classification:** `active` (≥1 non-suspended pane member is observed active **or cannot be proved gone**, or zero pane members exist — a poll-only or not-yet-registered team cannot fail the dormancy vote below, so it reads active) · `dormant` (has pane members and every one is either already suspended or positively observed `gone`; poll members abstain — a poll-only team is never dormant, its liveness is unknown by design) · `dangling` (index root no longer exists) · `unreadable` (root exists but its bus/registry could not be established — missing `.tap/bus` entirely, or a `registry.json` that fails to parse). The conservative `active` team label is not a claim that every member is reachable: seat detail still distinguishes `offline` and `unknown`. `unreadable` is never silently folded into `active`'s "zero agents" case — a team we failed to read is a cannot-check condition, not an empty-and-fine one.
- **`attention[]` — the sweep contract** (primary consumer: the hermes interval cron). Pre-triaged flags, not a team dump. Entry shape: `{team, handle, state, why, obligations: {inbound_unsettled, outstanding_unsettled, sample_ids}}` — `why` is one sentence naming the evidence, and `sample_ids` gives the investigator direct payload breadcrumbs.
- **Signals (v1, closed list):** (1) seat idle-at-prompt with unsettled inbound — the dropped-queue wedge; (2) seat state `wedged` or `rate-limited-error`; (3) pane dead while registry status is still `active` — the why sentence carries a `registered <age> ago` breadcrumb (killed-vs-never-existed isn't observable — registration captures a live `pane_id`, tmux records no death time — but how long the entry has been registered is); (4) stale outstanding send — a payload sent by the seat with no `.done` after `--stale-after` seconds (default 900) — the sender-side of the same wedge. Deferred by name: payload-imbalance heuristics (false-positive on legitimate lead fan-out), archive-bloat (belongs to `tap doctor`), and a `--since` delta mode (revisit if full dumps prove expensive for the cron).
- **Exit codes:** `0` the sweep ran, attention or not (CLI-EXIT-0; `tap health` is the check verb) · `1` cannot-check (the machine index itself is unreadable, OR any single enrolled team is `unreadable` because its registry is **present but corrupt**). "Can't check" must never read as "nothing wrong": the sweep wrapper alarms on `1` and on `0` skips LLM judgment when `attention[]` is empty. **A cannot-check condition outranks attention**: one corrupt-registry team forces exit `1` even when every other team is quiet AND has real attention items. A **data-gone** team (`dangling` root, or `unreadable` because the registry FILE is missing) is NOT a cannot-check alarm — it is a purgeable nudge (see below), so a dashboard whose only oddity is missing teams still exits `0`, never `1`.
- **Missing-team summary (tap-25p).** The data-gone teams refresh would purge (`dangling` + registry-file-missing) are recurring noise for the cron. Default TEXT output folds them out of the per-team list and out of the `cannot-check:` detail, replacing them with a single bottom line: `tap admin dashboard: N missing team(s) detected - run tap admin refresh to purge them`. `--verbose` restores their per-team rows and cannot-check detail. A present-but-corrupt registry always keeps its `cannot-check:` detail (it is a real anomaly, not just deleted). JSON is unaffected by this fold — it stays fully detailed, adding a `missing: [{team, reason}]` array (`reason` ∈ `root_gone`·`registry_missing`) alongside `cannot_check[]` (corrupt only).
- **Two distinct exit-1 shapes, by failure scope.** *Per-team* cannot-check (some teams unreadable, the sweep itself ran) produces the ordinary dashboard report, and there the JSON's `attention[]` and `cannot_check[]` are always BOTH present (empty or not) whether the exit is `0` or `1` — a wrapper alarms on the exit code and still reads both arrays in the same pass. *Whole-sweep* failure (the machine index itself is malformed/unreadable — there is no report to give) is an ordinary structured failure like every other verb (§Structured failures): exit `1` — JSON `{"ok":false,"error_class":"registry_invalid",...}` on stdout in `--json` mode, or one human line on stderr in default view — the dashboard never fabricates an empty report shape for a sweep that did not run. A wrapper branches: `ok:false` → infrastructure alarm; otherwise exit `1` → partial sweep, read `cannot_check[]`.
- Default output is the human table (with a `cannot-check:` section when non-empty, plus the missing-team summary line above); `--json` emits `{teams: [...], attention: [...], cannot_check: [...], missing: [...]}` — all four keys present even when their arrays are empty — on every run that produces a report (i.e. whenever the machine index was readable); `--full` adds full per-seat detail and `--verbose` un-folds the data-gone teams (both for debugging, never the sweep path). Size discipline: quiet-tick JSON ≈1KB (empty attention), flagged ticks ≤~10KB — the bound that keeps the judge's pass cheap.

### `tap admin refresh [--dry-run] [--json]`

The machine-wide **seat-trim + data-gone-purge** mutation — reconcile pane-backed registry rows with observable tmux reality across every enrolled team, and remove teams whose data is definitively gone from the index. Removing a **live** team from the index is still `retire`'s job alone.
