**Harness-level environment (tier 2).** `[harness.<name>.env]` in `config.toml` declares machine policy for every seat of one harness, so a value is stated once rather than repeated in every preset. It runs the identical key fence as preset `env` and refuses `harness_env_forbidden` naming file, table, and key. Unlike preset values it is **read at invocation time and never persisted**: it applies on every launch, resume, and restart — the paths that build an invocation — so a row created before a policy existed observes that policy on its next resume, and no registry migration exists or is needed. `repair` is not one of those paths: it reconciles registry and pane attestation and never builds a child invocation. The effective child environment composes in this order, later winning: the launcher's own Claude defaults (tmux truecolor, scroll speed, `CLAUDE_CODE_DISABLE_AGENT_VIEW=1` only; `setdefault`, deliberately parent-honoring); the harness table; and the row's own `harness_env` (preset- or `--env`-derived). Seat intent therefore outranks machine policy. Apart from the Codex auto boot stamp (below), the invocation builders originate NO environment: the middle tier they once supplied is deleted, so a per-harness built-in can no longer shadow a harness-table key, and the final re-write that forced `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` for a Claude row carrying `teams` is gone with the `teams` field itself — agent teams is spelled as environment like anything else. Supported keys in `[harness.<name>]` are `env`, `params` (the same params shape as presets), `permissions` (below), and `driver` (the courier's delivery door for that family — see the delivery-driver section; the launcher validates the key's presence and never reads it). Builder argv is the floor for CONFIG-SOURCED tokens — preset params and harness-table params splice through the same exact-token helper, so config can only ADD. Operator-typed passthrough (the pnpm-style tail persisted on the seat) inserts unconditionally: an explicit flag the builder also emits still lands. Config was the subject of the floor; the operator is the stronger authority. A valued param already in argv (from the builder or from an earlier tier) keeps its value; a later tier cannot replace it. For Codex config assignments, this floor applies per assignment key: a preset effort and a harness service tier coexist. Explicit config assignments override the same key from the builder or preset; preset keys outrank harness defaults. Within one vector, the last assignment to a key wins. Losing assignments are removed; surviving tokens retain their order and spelling. Config-key scanning stops at the harness `--` delimiter. Boolean flags are additive: `true` for a flag already present is a no-op, and `false` declines to add rather than turning a builder-owned flag off — that is the floor, not a missing off-switch. Both an unrecognized harness table name and an unrecognized key inside a recognized one emit a notice naming it — a silently ignored table or key is indistinguishable from one that had no effect, which is the "I seeded it and nothing happened" failure. TAP stamps the host boot id into the seat (the sandbox denies `sysctl`); it attests boot only. Auto refuses `--profile` and a user or project Codex config (start directory up to the repo root) allowing extra proxy sockets (`harness_permissions_conflict`). Cursor maps bypass to `--force --sandbox disabled` and auto to `--auto-review` (its server classifier runs safe tool calls and prompts for the rest; Cursor's own sandbox setting applies); AGY maps bypass to `--dangerously-skip-permissions` and auto to no flag (AGY has no automatic-approval mode and stops on every permission request). **A preset is complete.** `--preset` combined with `--model`, `--effort`, or `--env` refuses `preset_not_composable` rather than choosing a winner. **An allowed env key can steer a child seat's own preset lookup.** The key fence lists what a preset may NOT set; it is not an allowlist, so harness-home and config-directory keys such as `CODEX_HOME`, `XDG_CONFIG_HOME`, and `GIT_DIR` pass. `XDG_CONFIG_HOME` is the one that reaches the preset system itself: the catalog is read from the `tap` directory under it (`config.toml`, or the legacy `presets.toml` when `config.toml` defines no presets), so a preset that sets it changes where the CHILD seat looks for presets if that seat later launches one of its own. The launch that applied the preset is unaffected: resolution happens once, in the parent, before the child is spawned, so a preset's own env cannot change how that preset was read. For that reason `XDG_CONFIG_HOME` stays off the deny list; listing it would break legitimate config-directory redirection. This is a stated openness with a named remedy, not an oversight: if a real incident shows the child-seat effect causing harm, expand the fence then.

Resolution completes before registry, tmux, or child effects.
