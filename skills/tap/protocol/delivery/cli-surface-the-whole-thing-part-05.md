Unknown top-level tables (with a closest-known-key suggestion, so a `[preset]` typo is caught rather than silently dropped), unknown or future `version` values, unknown keys at any depth, and undefined `[roles]`/`[intelligences]` references are all NOTICES, never refusals. Every `metadata.*` key is carried VERBATIM rather than filtered against a whitelist, and display surfaces render unrecognized fields labeled by key — so the operator can add a field and reading models can work out what it means with no code change. The **only** remaining hard failure is a document that will not parse (bad UTF-8 or broken TOML syntax): without a document there is nothing to partially understand, and callers already own that degrade path. This rule exists because a reader that refuses what it does not recognize turns every extension into an outage: a single unrecognized table beside a valid preset list is enough to refuse every preset operation on the machine.

Degradation is scoped to the **smallest unit that still makes sense**, which is what keeps "ignore what you do not understand" from becoming "advertise what cannot launch". A file-level problem costs the file's unknown part, never the file; an unusable PRESET is dropped and named while its siblings load, because `harness`, `params`, and `env` decide what EXECUTES and an entry this reader cannot make sense of there is genuinely unusable; and a metadata problem costs only that FIELD or that ROLE, because nothing under `metadata` reaches argv or the child environment. Three consequences are load-bearing rather than incidental. A preset named after a canonical harness is DROPPED, which preserves the preset-first/harness-fallback equivalence exactly as the old hard refusal did — the lookup misses and falls through. A **retired** version reads no presets at all, unlike a **future** one which reads what it recognizes: the v1 layout puts `model`/`effort` at preset top level, so parsing it under current rules emits unknown-key complaints that tell a stranded operator to DELETE the key when the remedy is to migrate the file. And a role appearing in more than one bucket is dropped from EVERY bucket, since keeping the first would make the surviving ranking depend on iteration order and could let a `banned` role read as merely discouraged. The key fences still fence: a preset whose `env` crosses the identity, transport, process, credential, or policy fence never resolves, so the value never reaches a child — it is rejected by being dropped rather than by taking the file down, and the notice names the key without echoing its value.

A direct canonical harness with no `--preset` performs **no preset catalog resolution**; it reads `config.toml` only for `[harness.<name>.env]` (below), and that read can never block it. An **absent** config resolves the harness tier empty and silently, because a machine with no config is a legitimate state rather than an error. An **unreadable, malformed, or insecure** config resolves the tier empty, allows the launch or resume to proceed, and emits one notice naming the file, the fault, and the fact that policy is NOT being applied — the harness then sees its own upstream default, which is louder rather than quieter. Only a **well-formed** config whose `[harness.<name>.env]` crosses the key fence refuses, and that refusal is scoped to the named harness: a bad key under one harness never strands another harness's seats, including one cohort of a `resume --all`. An explicitly requested `--preset` keeps the fully fail-closed contract in every arm — tolerant reading changed which refusal it is, never whether it refuses. A preset the reader dropped (§Schema tolerance) fails `preset_not_usable`, naming the file, the preset, and the reason, rather than `preset_not_found`: the preset IS defined, so "not found" would send an operator to re-add something already there instead of fixing it, and the case where that misdirects hardest is a fence-crossing `env` key. A name genuinely absent from the file still fails `preset_not_found`; the two are distinguishable or neither means anything. The polarity split is deliberate and load-bearing: resume is the recovery verb, so a config error that blocked it would withhold the seats an operator needs in order to repair the file that is blocking them.

Accepted intent has three shapes: `launch <preset> [name]`, `launch --preset <preset> [name]`, and the compatibility form `launch <harness> [name] --preset <preset>`. The compatibility harness MUST equal the resolved preset harness or refuse `preset_harness_mismatch`. An explicit `--preset` miss is `preset_not_found`. The opt-in Bun launcher instead reports `preset_config_retired` when a requested preset belongs to a version-1 catalog, with migration guidance; direct-harness launches retain notice-only behavior. An unknown first positional is ambiguous by construction and refuses `harness_or_preset_not_found`, naming both harness and preset namespaces plus the canonical harnesses and any loaded preset names. Canonical harness names are reserved; a same-named preset is omitted with a notice rather than invalidating the catalog. `--preset` / `--preset=<name>` are launcher-owned everywhere: after implicit or explicit harness passthrough begins, either spelling refuses `preset_passthrough`; it MUST never enter the child argv. A numeric preset name does not enter the legacy numeric resume shorthand. When a preset launch omits `[name]`, the new seat's handle defaults to the catalog spelling of the preset name, including dots (`tap session launch sol.max` → handle `sol.max`, distinct from `sol-max`); an explicit name still wins. An observed-gone row colliding with that default produces a NEW seat with an automatic numeric suffix (`sol-2`), never through the identity-fork/suffix-mint path. A row that is not observed dead (including active, launching, or unobservable state) instead uses the existing on-roster chooser on a TTY and refuses with exit 2 and next-handle guidance without one. `--new` explicitly chooses a suffixed seat; `--fresh` explicitly replaces the incumbent under the existing replacement guards. A direct canonical-harness launch with no preset still defaults to the harness name. A preset whose catalog name is the reserved handle `help` refuses before registry or tmux effects; pass an explicit seat name or rename the preset.

The catalog is UTF-8 TOML with an integer `version` (`2` or `3`), a `[presets]` table, optional top-level `[notes]` string values, and optional `[roles]` and `[intelligences]` tables of string descriptions. Per §Schema tolerance above, NONE of that shape is enforced by refusal: a newer version reads what this release recognizes, a retired `version = 1` reads no presets at all and says so (its layout differs, so parsing it under current rules would emit unknown-key noise telling a stranded operator to DELETE keys when the remedy is to migrate), and the notice names the copy from the checked-in reference over the live machine file after a backup. Role keys live in `[roles]`, never as top-level keys and never inside `[harness.<name>.env]` — a TOML table stays open until the next header, so placing role strings after a harness env table would silently become environment keys. Preset parsing runs in the native Bun engine, so it imposes no interpreter requirement beyond the ordinary launcher's Python 3.10 runtime floor; there is no separate Python-side TOML dependency for it. Unknown top-level tables are ignored with a notice naming them and a closest-known-key suggestion, never a refusal. Preset names match `[A-Za-z0-9][A-Za-z0-9._-]*`. Each `[presets.<name>]` requires one canonical `harness`; the only optional keys are `params`, `env`, `family`, inert `description`, and inert `metadata`. Unknown keys and unusable values emit notices and drop the smallest unusable unit; a requested preset that no longer resolves still fails explicitly. The retired first-class `model`/`effort`/`provider` keys are not tuning inputs; the tolerant reader reports and ignores them as unknown keys. `params` is a table of verbatim CLI flags: TOML typing is the discriminator (boolean `true` → bare `--key`, string → `--key value`, string array → repeated `--key value` pairs in array order (empty array → omitted), `false` → omitted). `params.model` when a string populates the persisted model field; every other param becomes passthrough argv. Config params do not consult §Tuning translation (that table remains the CLI `--model`/`--effort` owner). `false` declines to ADD a flag and cannot turn a builder-owned flag off. Codex `-c` and `--config` assignments compose by the key before the first `=`, including the `--config=key=value` and `-c=key=value` spellings.
