**Receive isolation:** a sender-bus canonical with foreign `to_team` remains on that bus for sender supervision, but it is never local inbound merely because its bare `to` matches a local handle. `tap poll`, the dispatcher pending-age warning, `tap recap` inbox and received history, `tap in` briefing inbox and received history, `tap refresh` owed-mail, the launcher inbox digest (team identity from `enrolled_team_name_for_root` / `resolve_team_registry_for_root`, never invented `<root>/.tap/team-registry.json` or `basename(root)`), crew-unregister inbound classification, `tap admin` dashboard inbound counts, goalie bus-activity for inbound, `tap team` down/shutdown per-seat unprocessed-inbound advisories, and already-settled open-id lists require `to_team` to be absent or equal the local bus team (shared predicate `addressed_to_local` in `tap_frontmatter.py`). `tap read` and `tap reply` refuse the foreign identity before any observation, settlement receipt, or outbound write. Absent `to_team` preserves only the pre-flip legacy/manual-relay handle-only contract; marker-live relays always resolve and stamp the target team.

**Supervision:** `tap outstanding <sender>` (with the sender's `TAP_HOME`) lists unresolved cross-worktree items alongside same-tree sends. When foreign `to_team` is stamped, the item is labeled `<to_team>/<to> [cross-team: settles on their bus]` (tap-g3o6 — the terse `outbound-relay` marker is retired; the explicit tag states WHERE the obligation settles so a reader can never conflate an outbound relay with a local inbound obligation), and JSON carries `outbound_relay: true` plus `addressed_team: <to_team>` and `settles_on: "peer_bus"`; otherwise (manual operator relay, legacy traffic, or a team-qualified local item) it uses the existing qualified/fallback display without that marker. After note read or ask reply, the item drains from `outstanding` as usual.

**Cross-team reply route (tap-g3o6 / tap-ltc8).** A cross-team reply answers `<from_team>/<from>`. An absent machine marker refuses `unanchored_bus` like every native verb; there is no pre-flip route through the sender bus's `registry.json`. WHO-authority is the sender team's acting registry from the authority sample — never the retired bus mirror (binding the mirror stamps predecessor instances). Unreachable acting registry refuses (`error_class=unreachable_team`); there is no bus-mirror fallback. `--remote-registry <path>` on `tap send` still drives the team-qualified-remote delivery path off that explicit registry. `from_team` remains the display qualifier. The reply's own outbound canonical and receipt placement are unchanged (canonical on the replier's bus; `.done` on the sender bus via `--payload`).

**Actor on a cross-team reply (tap-g3o6, fork B):** `tap reply` derives the actor from the calling pane's registered handle when it resolves; when it cannot, the `no_actor` error **prefills** the exact `--by <to>` taken from the payload's addressee — it never auto-adopts it. Settlement provenance is an explicit actor claim: the caller re-runs with `--by` so the identity that lands in the durable receipt is deliberately asserted, not silently defaulted from the payload (TAP is a single-machine, consenting-panes trust model, so the prefill is a convenience, not a weakened gate). A bare `tap reply <id>` for a foreign inbound whose sender team is ENROLLED now resolves by scanning the enrolled team buses for the globally-unique payload filename (tap-akt4), so the universal reflex just works; only a miss on every enrolled bus (an un-enrolled peer — the index is routinely incomplete, tap-j20w) falls back to the `not_found` that teaches the absolute-`path=` `--payload` form. The scan is a best-effort convenience, never authoritative — `--payload` (the self-contained sentinel path) remains the override.

**By-id resolution on a local miss (tap-akt4).** `tap read <id>` for notes and `tap reply <id>` for asks resolve a local miss across enrolled team buses. They write observation or settlement receipts on the resolved sender bus. Ambiguous ids refuse rather than choosing a bus. For an explicit pointer, use `tap read path=<file>` or `tap reply <id> --payload <file> -f <answer>`; reply's settlement primitive retains its canonical-path and evidence checks. Public done never settles, including when its id resolves across buses.

**`tap poll` states the polled team (tap-g3o6):** `tap poll` lists **this bus's inbound only** (a payload's `to_team` must equal the local `team.name`, or be absent). It now names the polled identity — a human header `tap poll: inbox for <team>/<me> ...` and JSON `team: <local_team>` — so a cross-team obligation (which lives on the *sender's* bus and surfaces under `tap outstanding`, never `tap poll`) can never be misread as a local inbox item. poll = my-bus inbound; outstanding = my outbound (including cross-team relays that settle elsewhere) — the two are never conflated.

**Verify a cross-team send landed WITHOUT a false invariant (tap-g3o6):** a cross-team payload's canonical lives on the **sender's** bus at the location resolved by the sentinel’s qualified id or fallback `path=`; the peer's `payloads/` directory is *intentionally* empty of it. Check transport evidence with (1) `tap send`’s `status` and `delivery` fields, distinguishing verified pane submission from spool/poll acceptance, and (2) the payload on **your** sender bus; neither establishes recipient processing, and listing the peer’s `payloads/` directory tests the wrong residency. Listing the peer's bus for a foreign-`to_team` payload tests a false invariant and reads healthy delivery as failure (the specimen misdiagnosis this rule exists to prevent).

**Private reply settlement structural guard (F2B-2):** before deriving the sender-bus home, the `--reply-payload` primitive requires the payload path to have `payloads` as its immediate parent directory — i.e. the shape `<bus>/payloads/<id>.md`. Paths like `.../notpayloads/<id>.md` are rejected with a clear error. This is NOT a prefix allowlist (arbitrary absolute paths under any worktree root are accepted); only the directory hierarchy shape is checked.

**`tap outstanding` cross-worktree labeling (F2B-1, tap-18so):** cross-worktree items carry the authoritative `cross_worktree: true` envelope field. `tap outstanding` reads this field directly, so a cross-worktree item is recognized even when the sender has no `registry.json`. A `to_team`-stamped item is labeled `<to_team>/<to>` instead of the generic tag; when that team differs from the sender bus it additionally carries the human `[cross-team: settles on their bus]` tag / JSON `outbound_relay: true` (+ `addressed_team`, `settles_on: "peer_bus"`). `[cross-worktree]` remains the fallback for items with no known target team (a manual operator `--cross-worktree --pane` send, or legacy traffic). A further legacy fallback heuristic (recipient absent from registry) still applies for payloads predating the `cross_worktree` field entirely. `tap health`'s unsettled-payload listing applies the same `<to_team>/<to>` / `<from_team>/<from>` rendering when those fields are present.

**What does NOT change:**

- Same-team sends (`tap send <to> <payload>` or `tap send <local-team>/<to> <payload>`) remain worktree-local and registry-scoped. The envelope's `cross_worktree`, `from_team`, and `to_team` fields are NOT stamped on normal sends, and the envelope `from`/`to` remain bare team-local handles, while the same-team v0.23 sentinel carries a bare message id (tap-cnfm).
- `tap register` still enforces the same-worktree guard when the caller is in git (Unit 1); cross-worktree relay is a send-side mode, not a registration change.
- `tap doctor` warns (`WARNING: EXTERNAL-PATH`) when a payload's `path` field points outside the local bus — this catches misplaced payloads but does not fail-hard (it is a WARNING, not a TORN finding).
