- **Target identity is bound once, at park time, and never guessed afterward:** the courier stamps the spool entry's `pane`/`pane_id`/`to_team` plus `target_registry`, the exact local or foreign registry selected by the originating send. Later checks may re-read only that bound registry; they never resolve the stripped bare `target` through the drain caller's registry or repeat team discovery. Whenever `to_team` is non-empty, the bound registry's `team.name` must equal it both when the entry enters the spool and at drain/redelivery; a missing or inconsistent binding stays parked with `reason=legacy_meta_no_binding`. A handle string is not a stable cross-team identity, so a legacy cross-team entry without `target_registry` fails closed. A stale-but-internally-consistent registry that still claims the stored handle/pane/pane_id for a different occupant cannot be distinguished by any pane-id predicate; detecting that residue is out of scope without an opaque generation token.
- **A drain acts on complete publication snapshots.** Spool bodies and metadata are published separately. A row whose metadata could not be read is incomplete even if that file appears before a later existence check; it waits for the next snapshot and cannot mark a newly completed binding as missing. The original registry and pane checks still govern every complete row.
- **Readiness** is re-checked from scratch every attempt, never cached: the target row in `target_registry` must still bind the stored handle to the stored pane and `registry pane_id == stored pane_id == live pane_id` (else `gone`) → harness not denylisted/unsupported (else `unsafe`) → copy-mode checked **read-only** (`#{pane_in_mode}` peeked, never cancelled here — cancelling on every readiness poll would kick a human out of copy-mode roughly once per tick_interval while they scroll; the actual cancel-then-inject happens only inside a genuine redelivery attempt, below) → a same-team blocked seat (`blocked_map`/`blocked_exempt`, `to_team` empty only — a cross-team entry's handle string has no relationship to this team's blocked-map) is not ready either → THEN a pane-native idle check (native `pendingInputText`, not the handle-keyed `tap_seat_state`). Any earlier failure is `unsafe` or `gone`; a still-busy pane (no visible input prompt, in copy-mode, or blocked) is `busy`.
- **Ready** entries redeliver now: the spooled payload moves back to the real canonical `payloads/<id>.md` (never re-placed through `canonicalPlace` in runtime/bun/src/courier.ts — it is already fully stamped, so this is a direct move). Copy-mode is cancelled HERE, immediately before injection (not during readiness) — the one point where an actual delivery is genuinely about to happen. The EXACT original sentinel is rebuilt via `renderSentinel` (runtime/bun/src/sentinel.ts — the single shared source of truth, so a second injection site can never drift from `tap send`'s own construction; slash-qualified the same way, `<team>/<handle>`, whenever `from_team`/`to_team` are stamped), then injected + verified. `0`/`5` (delivered/queued-unverified) both remove the entry — the same "durable" bucket every other watch send site treats identically. Anything else re-spools the ORIGINAL payload untouched; a failed redelivery attempt never loses the message.
- **Deadline branch is mechanical, never re-inferred** (round-2 review): the spool entry carries its park reason as a `reason_class` — `busy` (an ordinary no-input-prompt wait) or `safety_gate` (copy-mode) — decided once, at spool time, from the reason string. Once `deadline_epoch` is reached (derived from a polite timeout plus its grace, or directly from a watcher probe's `probe_timeout_seconds`):
  - `reason_class=busy` **and** currently re-confirmed safe (not `unsafe`/`gone`) **and** not yet escalated → force-inject despite still being busy (the timeout-degrade to default injection the plan promises). Once an entry has escalated (`escalated_at` set), this branch stops for good — post-escalation an entry delivers only on a genuine `ready`, never on a repeated forced attempt (no per-tick churn, no surprise forced injection long after a human was already notified).
  - `reason_class=safety_gate`, **or** the entry is CURRENTLY `unsafe`/`gone` regardless of its stored `reason_class` (a busy entry that became unsafe since spooling must not silently wait forever either), **or** a forced-degrade attempt itself failed to land (e.g. a non-prefix harness still showing no prompt) → **never** force-inject (again, once already escalated). Escalates via the same sticky-NOTIFY channel chain exhaustion uses (one human escalation surface, not a parallel one) and stays doctor-visible; the entry is NOT removed from spool by escalation, only a successful redelivery or explicit human cleanup removes it. Spool escalations dedup **per-entry** (the spool meta's `escalated_at`, set once), NOT through the episode-scoped `notified_at` a wedge exhaustion uses (tap-t4i): a spool timeout that escalates while no wedge episode is active must not poison that shared slot and silently eat every later independent spool NOTIFY — so an unrelated spool entry timing out in the same armed run always raises its own fresh NOTIFY. `escalated_at` gates the human NOTIFY itself, not just its own write: escalation runs on every past-timeout tick, so a given stuck entry NOTIFYs **exactly once**, on its first escalation, and never re-pings the operator on later ticks (which would otherwise happen once per `tap watch ack`, since ack lapses the sticky-pending guard). An unrelated entry's first escalation still fires while a prior NOTIFY is unacked by merging under that same sticky-pending guard. This is the absolute form of "the classification/safety gate is never bypassed by any policy."
  - No `deadline_epoch` at all (an ordinary default-origin auto-spooled entry; watcher-owned probes and pending-input drafts are the bounded standard-policy exceptions) → no timeout, ever: it waits until it can redeliver, surfaced only by `tap doctor`'s age-based stuck-spool flag (below). "Never spool-forever" is not a guarantee extended to every defer.

**Pane-tint parked indicator.** The watch spool pass (`runtime/bun/src/spool-watch.ts`) does not paint `bg=colour22`. `hold_until_epoch` says a row is eligible, not that it will inject, and a standing tint showed while busy, grace, and unverified rows were still parked. The pass untints every pane still named in the arm record's `tinted_panes` and then records an empty list, so an older arm cannot leave that tint up. `tintPane` — pane-scoped `tmux set-option -p -t <pane> window-style bg=colour22 ; set-option -p -t <pane> window-active-style bg=colour22` (runtime/bun/src/pane-tint.ts) — remains the primitive those older records used. Clearing UNSETS the two pane options (`set-option -p -u`) rather than writing `bg=default`, so TAP removes exactly what an older arm set and the pane inherits again. Pane-scoped, never `select-pane -P`: moving pane_active steals keyboard focus (tmux 3.7c). Cosmetic, best-effort ONLY — a tmux error applying or clearing a tint must never fail a park or a redelivery. `tap watch off` and `tap team reset` both call `clearTints` (runtime/bun/src/watch-sidecar.ts) BEFORE the arm record — the only tint-ownership record — is deleted or archived, so a crashed or disarmed watcher never leaves a pane permanently tinted.
