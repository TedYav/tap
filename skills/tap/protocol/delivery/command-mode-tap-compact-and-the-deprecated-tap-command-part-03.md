The shared courier observes an empty composer before typing but cannot atomically exclude human keystrokes between that read and injection; a detected prefix mismatch leaves input in place without retry or Enter.

OpenCode compaction binds the registered `session_store_path` (legacy rows may use `transcript_path`) together with the authoritative native session ID. Request creation, Enter capture, proof waits and resume authorization use that same store path; drift refuses further effects. No store discovery or registry repair occurs during compaction.

**The command palette is chrome, and exact-mode clears take the ordinary clobber pipeline (tap-e034).** Because opencode's clear spelling *is* a slash command, submitting it opens opencode's command palette — which draws its item list INSIDE the input box's own border, above the typed row. Popup rows are bordered on BOTH sides while a typed row carries only the left border, and the band reader excludes them on that structural test AND a border-colour test **together**, so the exact-match verify observes the typed text alone. Both halves are required: a structural-only rule also eats a human draft row that legitimately ends in the border glyph, and this reader feeds the pending-input backup, so eating a row means clearing text nothing can recover. Where the colour test is unavailable the rule KEEPS the row rather than stripping it (tap-d901): an unreadable discriminator stops the strip instead of licensing it, because this reader also feeds the pending-input backup, where a wrongly-eaten row means the clobber clears text that was never saved — silent and unrecoverable — while a wrongly-kept row makes the exact match fail and the clear refuse, which is announced and recoverable. The cost is named rather than hidden: chrome then leaks into the band for every consumer, and `tap nudge` is the one that would rather have had it removed, since its stuck-sentinel parse requires the region to BE the sentinel and refuses on anything else. That refusal is loud, which is why the polarity still falls this way. A new harness must not be given a structural-only version of this rule. This is load-bearing rather than cosmetic: that verify runs BEFORE Enter, so a reader that returned the item list glued to the typed text made every opencode clear fail `input did not land` without ever submitting — a verb that could not succeed on the one family it was written for. Relatedly, On OpenCode submit exit 5, the shared helper records the first escaped composer frame at `$TAP_HOME/receipts/<id>.opencode-submit-unverified.ansi` before releasing its submit lock. Capture uses `-e -p -J`, rechecks bound identity, and is best-effort: capture failure never changes exit 5. An unreadable composer boundary retains the captured frame for diagnosis. OpenCode excludes a band opening with `[[TAP` from its non-chip pending-text skip: a readable stuck sentinel is submitted first, and an unparseable anchor refuses intact before a later send can append. `match_mode=exact` also bypasses that skip: exact-mode control input takes the same sentinel-first / backup / `C-u` pipeline every other harness takes, because skipping it left a failed clear's own text in the band for the next attempt to type on top of (`/new/new`, which matches no command at all — a retry strictly worse than the first failure). Ordinary opencode sends keep the existing skip.

**The clear half's success contract is retired with it (tap-pz3j), and its two most specific guarantees did not move — they had no analogue.** This paragraph used to specify the injection clear: an exact `/clear` submit, then `tap register <same-seat> --pane <same-pane>` preserving `cost_mode`, `include_policy`, `unattended` and `reply_to`, then a standing-brief recovery prompt. All three followed from the clearing command RE-REGISTERING THE SEAT ITSELF, which `tap clear` does not do — the fresh process registers from its own environment (§Seat clear). So the option-preservation guarantee has no successor, and neither does the rule that a preserved `reply_to` must resolve to a currently deliverable non-self seat BEFORE the clear was submitted: that preflight existed to avoid discovering a broken reply route after the context was already gone, and there is no longer a re-registration to preserve a route across. Recorded rather than deleted, because a guarantee that quietly stops existing is worse than one that is stated as retired; the smoke arm that pinned it carries the same verdict at its old site in `command-mode.test.sh`.

**The audit ladder is now single-stage, because its three-stage form was the clear half's (tap-pz3j).** Compact prepares its single `success` audit before pane input, refuses untouched if that canonical payload or receipt cannot be prepared, discards it on a failed submit, and publishes it only after verified submission — so a compact either has a verified audit or has no audit. The retired clear half additionally staged `cleared` and `partial` records around a point-of-no-return, with `command_prior` linking the terminal record to the `cleared` one; that ladder existed because an injection clear could succeed at the pane and then fail at re-registration, a partial state `tap clear` does not have (§Seat clear owns its own partial states, and `tap refresh` translates them — §Seat refresh).

Every published audit is a canonical `kind=command`, `reply=settle-only` payload from the initiator to itself with `command_target`, `command_verb`, and `command_status`, plus an atomic `.done` receipt whose `by` is the initiator and whose typed `auto` field is `true`. This records the action without forging settlement by the target seat.

Writer Token custody is deliberately outside the CLI: `/tap:context` must refuse context changes while a seat holds a lane token. The transport cannot infer authoritative runtime custody state.
