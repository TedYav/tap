**Codex seat activity (tap-92vi).** The seat-state busy gate uses the shared Codex screen observer on an ANSI-preserving capture. A live `Working … esc to interrupt` row within the last four nonempty rows above the dim-painted empty composer reports `working` before empty-prompt or recent-activity fallbacks. A quiet painted composer reports `idle-at-prompt` even when courier traffic advanced `window_activity`; old working rows outside that region and typed placeholder words do not establish a busy footer. The status line is configurable and is not required. This activity observation does not certify submission.

The opencode lesson lives inside the helper: key on the active input band / id clearing, NOT footer text or tail-N of rendered history. On opencode a naive tail/footer match false-matches against rendered history forever; on Codex the `[›❯»]` input line is the signal. **claude is glyph-line for the PROMPT and status-row-gated for BUSY (tap-4n5h, tap-7txco):** its band is always drawn, so glyph presence cannot distinguish generating from ready. Current Claude Code no longer paints `esc to interrupt`; the positive busy evidence is the live spinner row (`✽ Elucidating… (running PreToolUse hook · 1m 19s · ↓ 5.5k tokens)`), read only from the status row above the band (`claudeStatusRow`): the nearest row starting at column 0. Every live row Claude paints between the spinner and the band is indented — queued messages (`  ❯ …`), `  ⎿  Tip:` blocks, right-aligned notices such as `✔ Update installed` — and a row under a full-width row is a wrapped continuation, so all of them are skipped. The row needs a spinner glyph, a present-tense verb with an ellipsis and an elapsed clock inside the parenthesis. The past-tense done line (`✻ Brewed for 42s · done 5:59 AM [· N shells still running]`) never reads working, and neither does the same shape in older transcript, a tool row, or the composer, because the string occurs in ordinary text and a whole-pane match would pin a seat discussing it to `working` forever. The older footer `esc to interrupt` arm is kept for Claude builds that still paint it, matched only in the live footer. A permission dialog stays `blocked` over a spinner. Claude frames carry the same `busy` pre-state reading as OpenCode (tap-ho6pk): a quick-starting turn after the courier's own Enter (empty composer, the wire now in the transcript, spinner running) relabels to `injected` when the earliest read of that submit was idle, and keeps `harness_queued` when the seat was already mid-turn. Before the footer arm existed, a generating claude seat fell through to `idle-at-prompt` — the false-idle that made a working board report WORKING==0, and it returned when the footer hint was dropped until the spinner arm landed. Hermes keeps that glyph-line model, but a named profile may prefix the idle prompt with a token (`ops-hermes ❯`); only `[A-Za-z0-9._-]+ ` is accepted before the glyph, so the working `⚕ ❯ ...` prompt is still non-idle. The band itself is anchored on **box geometry** — the run of `┃`-bordered lines directly above the last `╹▀` bottom border — never on a `▣ Build` header: since OpenCode 1.17 that marker is a per-turn transcript line that can scroll off entirely when box content wraps tall (observed live as a false `submit_unverified`). Band reads are chrome-normalized: the `┃` border, the mode·model footer row, and the sidebar-width right-aligned cwd/branch overlay are stripped, so only typed text (or a wrapped sentinel) counts as input. **Each strip requires evidence that the row IS that chrome, because this reader also feeds the pending-input backup and an eaten row is cleared without ever being saved.** The footer row is popped when it matches the mode·model grammar (`Build`/`Plan` followed by `·`), not merely by being last: that premise holds on every captured box, so the two rules agree on real input and differ only on a box with no footer, where popping blindly ate human text. The overlay is identified by the column its content starts in — measured at 99 and 116 across the captured boxes, against 1 or 2 for every human draft including wrapped continuations, which start at the left margin like any other typed row — so the threshold sits in the middle of that gap rather than at the draft class's edge. An earlier `>= 5 columns` rule read a five-space draft as chrome. Both strips therefore take the polarity the same-row overlay split already takes: **an unavailable or unconvincing reading keeps the row.** A kept chrome row makes the pane read occupied and delivery park, which is announced and recoverable; a dropped draft row is not. The residual is the other direction and is accepted: an overlay drawn narrower than any capture leaks into the band and that pane parks until its width changes. cursor-agent needs no adapter branch (generic `→` glyph + dim placeholder), but its prompt is not bottom-fixed — glyph-line searches window on the last non-blank row, not the pane bottom. **Placed-but-undelivered is not delivery failure (tap-92v3r).** A pane-mode payload whose recipient is demonstrably PRESENT is HELD past its readiness deadline rather than terminalized. Presence is defined by NAMING THE TERMINAL STATES, not by listing the live ones: `gone` and `unsafe` are the only classifications readiness (`runtime/bun/src/spool-readiness.ts` `readPaneReady`) returns before its bound-identity check passes, so every other value — `busy:noprompt`, `busy:pending`, `busy:modal` (a recognized dialog is asking that seat's human a question), plain `busy` (copy-mode, or a blocked/exempt seat), `busy:clearing` (a live clear fence), and `ready` reached after a pre-effect failure — describes a pane whose identity just matched. An allowlist of live states has to be re-derived every time a `busy:*` value is added, and forgetting one produces exactly the false delivery failure this rule exists to prevent; a denylist's failure mode is holding an entry that should have ended, which the roster exit resolves. The ordinary retry path keeps working it: past the deadline each drain forces one real redelivery, and a redelivery that cannot type re-parks pre-effect.

**And after a bounded number of those looks the courier types anyway (tap-7r3fn.13).** Holding instead of lying to the sender was only half an answer — a seat that is simply working never frees its band, so a held entry could wait indefinitely while the recipient was receiving other mail by hand. **After 3 post-deadline observations of a live pane (`TAP_SPOOL_FORCE_PROBES`), the drain injects even though the band is not readable.** This is sound because every supported harness except hermes QUEUES typed input while generating: the forced injection lands in the recipient's queue and is read at the turn boundary, exactly as an ordinary mid-turn send is. The observations are counted in the entry's own durable `busy_live_probes`, which is deliberately not `busy_pending_probes` — that one counts typed-text wedges and feeds the backlog CONDITION, and widening it would make ordinary heads-down traffic report as a wedge. Only a post-deadline, live, non-modal look pays toward the bound; a pre-deadline look, a `gone`/`unsafe` probe, and a drain that refused an unauthorized bus and attempted nothing all count for nothing, so the bound cannot be reached without real looks at a real pane.

**Held-entry refunds are bounded and rotate fairly.** A post-deadline readiness-gate entry that remains held may return its slot so younger deliverable mail is not starved, but one invocation grants at most `TAP_SPOOL_DRAIN_CAP` such refunds; otherwise every held entry removes its own charge and the cap stops bounding the per-ID pass. Phase B orders entries by `(held_drain_visits, first_spooled_epoch, id)`, so held mail deferred by that bound rotates ahead of the already-visited prefix while equal-count entries retain deterministic arrival order. The count belongs to the held state, not to the entry for life: Phase A clears it when that old entry becomes ready, before Phase B applies its cap, so a cap-sized stream of fresh mail cannot preserve a stale priority penalty and starve the deliverable old entry. Mark updates take the entry's meta lock without waiting; a skipped update may postpone accounting to a later drain, but never blocks the courier or authorizes an early injection. The digest-planning readiness pass still examines the spool independently; the bound governs the per-ID work pass, not that inventory.

**hermes is excluded, as a property of the harness rather than a carve-out.** Its bare un-prefixed inject IS its interrupt (§Delivery policies) and its queue is reached through the `/queue ` prefix, so forcing there would not deliver sooner — it would cut a working seat off mid-thought, which is the opposite of what the bound is for.

**Recognized modal, startup, and clear-fence holds survive the force bound.** The dialog case is `busy:modal`, produced by the agy permission overlay, which the pending-input reader reports as a modal hold rather than absent geometry; `busy:booting` and `busy:clearing` also remain non-forceable. That distinction is what makes the bound expressible: rc 3 means "nothing readable was here", an absence of evidence that the bound is allowed to push through, while rc 4 means "a human is being asked a question", which it may never type over. A modal is a **hold with a reason and is retried on every drain — it is never a `delivery-failed`**, and the sender is never told the message will not arrive. An Antigravity pane that is merely GENERATING is not this class: its band stays rendered, so it classifies `ready` and is injected on the FIRST attempt with no bound to wait out. Nothing re-enters delivery after a possible effect; submit-unverified still terminalizes on its own branch. The exits are unchanged — the band frees and the entry delivers, or the seat leaves the roster and the probe returns `gone`/`unsafe`, which terminalizes on the next drain.
