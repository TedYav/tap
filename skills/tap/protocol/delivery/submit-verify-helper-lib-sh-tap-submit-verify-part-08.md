  Position alone is unsafe when the suffix is not in the table. **Cursor paint is corroboration, never a requirement** — the reverse-video cell is usually not rendered at all (measured: painted in 0/12 captures at the production read beat, 0/20 at steady state, with the hint present in every one), so a rule keyed on it fails closed on the common render while fixtures that happened to catch the painted variant still pass. Both renders are pinned as fixtures for that reason. **Exactly** two, never "at least two": one or zero means a relocated cursor spent a column, and three or more is unreachable by typing, since a second space makes the harness drop the hint entirely. On any doubt — an unreadable pane width for the truncated form, or the plain suffix not ending the band — the band is left whole, which surfaces as this check's ordinary `5` refusal rather than as a silent cut.
- **The band reader's prompt geometry is explicit code points, not a locale's `[[:space:]]` (tap-bg19, tap-6zzsk).** The retired `tap_prompt_line_re` (now `promptLineReText` in `runtime/bun/src/pane/reader.ts`) printed ONE pattern, `^[[:space:]<NBSP>]*GLYPH`, and the shell then fed it to THREE programs whose implementations of that class disagree. Measured on macOS `/usr/bin/{grep,awk,sed}` under `LANG=en_US.UTF-8`, with a separator placed BEFORE the glyph: all three accept TAB/VT/FF/CR/SPACE and U+00A0; `grep -E` and `sed -E` additionally accept U+1680, U+2000–200A, U+2028/29, U+202F, U+205F and U+3000, which **awk rejects**; none accepts U+001C–001F, U+0085, U+FEFF, U+2060 or U+200B (a representative per row was measured, not every character of each range). The reader therefore carries TWO selectors, and which one a pane gets is **per harness**: Claude's prompt row is read out of the overlay capture the approval check already took, which the incumbent selected with `awk`'s NARROW class; every other harness re-reads through `tap_inputline`, whose `grep` class is WIDE. A caller that supplies its own frame gets the narrow one whatever the harness. Native land/clear (`observeInputRegion`) is awk-narrow too, except OpenCode and agy (tap-6zzsk).
- **That asymmetry is a live incumbent defect, ported byte-for-byte and stated rather than repaired.** On a U+2000-padded prompt row, a Claude pane reports **absent geometry** — status 3, the direction the draft-clear types over — while the identical row on Codex, Cursor or Hermes reports the draft it is holding. Measured against the pinned base by running it, both before and after the port. A second face of the same split: the region reader (draft backup, id matching) uses the narrow class for every harness, so a U+2000-padded row can be a draft to the pending-input reader and nothing at all to the reader that would back it up. Closing either is a behavior change with its own oracle, not a fold-in. Because the classes are now code points rather than a POSIX class resolved per locale, the tap-bg19 field class — a launchd tmux server with no `LANG`, `sed` matching bytes, two bytes of glyph residue read as typed input, every delivery parked as `pending-input` — is not reachable by any locale.
- **Input-ID matching preserves non-whitespace bytes (tap-ljf0h).** The shared native normalizer removes terminal CSI paint, normalizes Unicode to NFC, and removes the Python whitespace set used by the original reader. This includes U+001C–U+001F and U+0085, but excludes U+FEFF: an embedded BOM cannot turn a corrupt ID into the expected ID. The same contract applies to native composer comparisons and the pane reader; a matching ID proves visible content, not submission.
- **One capture per band read, and two where two are the point.** The incumbent's generic pending-input read took up to three separate samples — a plain prompt row, an escaped prompt row, and `#{pane_width}` — and could observe a band mid-redraw differently in each. The reader now takes ONE escaped capture and derives the plain view by removing SGR, which is what `capture-pane` without `-e` returns; the width is still queried for Claude alone, where it is the geometry signal for a truncated argument-placeholder hint. **The recoverability probe still captures twice**, because its instability arm exists to detect a band being typed into between two observations, and one capture read twice can only agree with itself.
- **"I could not read the band" is a distinct answer from "the id is not there".** The retired Bash band predicates (`tap_input_has_match`, `tap_input_has_injected_content`, `tap_input_has_paste_collapse`, deleted with the Bash submitter in R4) answered 0 yes, 1 no, and **2 could not read** — a missing runtime, a module that failed to load, or an unrecognized verdict. The submit loop treated only 1 as evidence that the payload left the band; a 2 takes neither branch, the loop looks again, and exhaustion refuses with `submit-unverified`. Reading an unreadable band as consumption would let a crashed reader certify a submit nobody verified — the incumbent had that hole by a different route, since a crashed match normalizer left an empty haystack that matched nothing and read as consumed.

  **Every consumer of a three-state predicate must branch on 1, never on "not 0".** Two call sites
  did not, and both were destructive in the direction the rule exists to prevent: the delivery
  disposition slice wrote `! tap_text_has_paste_collapse`, which turns rc 2 into "no chip" and blanks
  the composer — the inject-eligible direction; and OpenCode's staged-anchor arm wrote
  `|| tap_input_has_paste_collapse ... || typed_input=""`, where rc 2 falls through to the blanking
  arm and DISCARDS the pane owner's draft because a chip reader failed to run. The disposition slice
  is native now (`spool-readiness.ts`, where the chip predicate is total), and OpenCode's arm captures
  the status and acts only on a positive 1. `!` and a bare `||` chain are the two shapes that silently
  re-collapse three answers into two.
- **The prefix must own the whole input region, not merely the prompt line (tap-tx3s).** The reading above is one physical line, so a wrapped draft escapes it: at a narrow width a pane holding `/compact LEFTOVER-DRAFT-TEXT` renders its prompt line as exactly `/compact`, the line comparison passes, and stage 2 then appends the payload to that draft and submits it. After the line comparison succeeds, the courier additionally requires the active input region (`pendingInputRegionText`) to carry nothing past its first line; anything there fails closed (`unverified`) before the payload is injected. A region that cannot be read at all is also a refusal — it contradicts a prompt line that just read fine, and the cost of refusing is a retry while the cost of passing is someone else's draft submitted.
- **A scrolled composer proves the typed `/compact` from its visible suffix (tap-vho8h).** Claude's composer is a viewport of about the pane height minus fifteen rows (five rows at height 20, fifteen at 40, twenty-five at 60 on Claude Code 2.1.283). A focus that wraps past it scrolls the command row out of frame and repaints the prompt glyph on the first visible row, so the whole-frame match reads `changed` and the worker withheld Enter with the text left in the composer. On the typed-prefix `/compact ` arm only, the pre-Enter frame may stage from its visible suffix: the head was already proven on the prompt line before the first payload chunk and the tail read back after the last one, and every payload chunk is read back before the next one goes in (the visible rows must be a suffix of everything typed so far and end with that chunk, so the overlapping windows chain across the head and middle the final frame cannot show), so at Enter the courier requires every visible row to be an exact width-bounded slice of its own control under the same wrap rules as the full match, anchored at the marker and ending exactly at the control's end, with exactly one alignment. A prompt glyph on the first visible row does not make it the start of the control; other prose ending in the marker, a different marker, a `/goal` or `/loop` control, and an ordinary wire all keep the whole-visible-wire rule. The shared box readers are unchanged: a box with no prompt row stays unreadable everywhere. When the proof still fails after typing, the courier result, the worker's terminal receipt and its `self-helper.log` line say the text is in the composer, that Enter is the operator's move, and that nothing is retyped. `tap self compact` refuses a focus over 2,000 characters before any pane effect; detail belongs in the handoff.
- **A scrolled composer proves an ordinary wire from its visible tail (tap-1ncs6).** The same viewport hides the head of a delivered sentinel at a narrow width: at 38 columns a wire wraps over five rows, the `[[TAP v0.23 note <id>` head scrolls off, and only the tail is in frame. The id-anchored landing check then reported `input did not land` with the whole wire sitting in the composer, Enter withheld (`enter_count 0`), and the next delivery read that tail as a human draft and cleared it. One recognizer (`runtime/bun/src/sentinel-tail.ts`) now serves the landing check, the pre-Enter and post-Enter frame reads, the draft-versus-sentinel classification before any clear, draft protection, `tap nudge` and the recovery Enter guard. It decides on evidence, never on how text ends: a draft that closes with `]]` is a draft. For the wire this courier just typed, the band read empty before the paste and the visible text, joined and whitespace-free, is a suffix of that wire: the landing is proven and Enter follows. A tail found before typing gets Enter only as a suffix, id fragment included, of a wire this bus's courier recorded typing into that pane in this server generation (`typed-wires/`: last four, staged-idle window); the new delivery proceeds and nothing is re-injected. An unproven tail takes the draft path. `tap nudge` requires the same proof and presses Enter through its recorded recovery run with the argv target as the recipient. A narrow pane is a supported state; there is no width refusal.
- **On the typed-prefix arm a chip is never provenance.** The retired Bash arm resampled "did a paste-collapse chip exist before we touched the pane" after the prefix stage, so a chip formed during the settle could not be credited as payload landing. The native arm needs no sample: a chip there is always a refusal (part 6). The plain arm's chip-transition rule is unchanged.



**Observed failure:** in a live session, a TAP-delivered message reached the recipient's pane but was incomplete — the sentinel injected but the recipient appeared to receive only a partial message body.

**Classification / diagnosis:** The reproduction is **inconclusive**. Three candidate causes were identified:

1. **Courier submit/verify loop:** `tap-send.sh` verifies "id cleared from the input line," not "full payload body was consumed by the harness." The submit loop fires multiple Enters for claude/codex; rapid multi-Enter sequences could in theory cause double-submission or truncation at a TUI that buffers input differently under load.
2. **Harness paste-limit:** some TUIs have a maximum per-`send-keys -l` paste buffer. A long sentinel near the tmux paste limit could be silently truncated before it reaches the harness.
3. **Protocol misuse:** the payload BODY lives at `payloads/<id>.md` (the `path` field). If the recipient read only the inline sentinel text rather than the file at `path`, the body would be absent.

**What was built:** The factoring into `tap_submit_verify` preserves the EXACT existing submit+verify behavior (pure extraction, no logic change). The shared helper makes a future post-submit body-presence check possible in ONE place. No behavioral change to the courier was needed to unblock Units 1-4.
