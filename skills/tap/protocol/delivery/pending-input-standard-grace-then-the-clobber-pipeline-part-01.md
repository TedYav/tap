## Pending input: standard grace, then the clobber pipeline

**Human input in a registered pane is ephemeral by policy, but it gets one bounded grace window.** A real pending draft is accepted into `spool/` with `policy=standard`, one 30-second deadline, a green warning at park and a red warning in the final 10 seconds (urgent: ten seconds of grace and red immediately), `status=queued`, `delivery=spool`, and exit 0. If the band clears early, a shared drain delivers it. At the deadline, pipeline continuity wins and `tap_send` enters the retained backup/clear/submit path below:

**Claude dim chrome never becomes pending input.** A prompt row painted dim (SGR 2) from end to end is chrome, not a human draft: the empty composer's `Try "…"` suggestion (tap-ybz1s) and the `Press up to edit queued messages` placeholder beside indented queued rows. The pane reader captures Claude with escapes and decides by paint, not text, the same rule the submit reader applies; typed text, a partly dim row and a paste chip stay input. This state parks no standard-grace draft, earns no green/red cue, and never enters the clobber pipeline below. The positive queued-input hold remains Codex-specific.

**OpenCode's first-load placeholder never becomes pending input.** A fresh seat's welcome screen draws `Ask anything… "…"` in the typed-text position, distinguishable only by its pinned gray paint. The owner-delivery pane observer therefore captures OpenCode with escapes, as the submit and region readers already did; a plain capture read the placeholder as a draft and refused every first delivery to a new seat (tap-yqonr). Typed text on the same screen stays input.

1. **Sentinel-first:** if the pending text is itself a stuck `[[TAP v0.23 ask|note <id> …]]` sentinel (a prior courier inject that missed its Enter — the exit-5 class), it is **submitted**, not clobbered: Enter delivers that message, then ours injects behind it. Clobbering it would orphan the prior send's canonical. The pending text is a sentinel whether it shows the `[[TAP` opener or only the tail of one: Claude's composer viewport scrolls a long wire's head out of frame at a narrow width (tap-1ncs6), so the classification uses the shared shape rule in `sentinel-tail.ts` — anchored on `[[TAP`, or closing with `]]` and carrying a piece of the wire grammar (a `preview="…"` or `path=` field, the closing quote of one, or an id-shaped fragment). A scrolled tail is submitted like an anchored sentinel, by shape and without naming which wire it is; text that fails the shape is a human draft and takes the backup pipeline below. Recognition is by class, not identity; see SECURITY.md, "Failure modes TAP does not defend against".
2. **Backup + bounded recovery decision:** any other text is written to `input-backups/` first (policy `clobber`), capturing the full chrome-stripped active input region rather than only its glyph line. Claude and Cursor terminate that region at their input-box geometry — respectively Claude's bottom border and Cursor's closed `▄`/`▀` block borders around its `→` prompt — never by footer wording. Claude recognizes only a U+2500 (`─`) run of at least 10 cells as its border; an identical run in a human draft is the accepted rare-loss ambiguity and terminates that region. Codex has no such box, so its model/context status row is terminal chrome; a wrapped status row is recognized across bounded trailing physical rows. Cursor uses one bordered-box reader in `submit-frame.ts`, shared by Bash, native observation, and nudge; background tint is not an identity signal. If the bounds are missing or ambiguous, TAP backs up only the already-classified prompt text and takes the bounded clear-and-withhold path rather than guessing from footer/status chrome. Complete plain text is eligible for the bounded line-by-line post-submit restoration below, regardless of captured row count. Incomplete paste/image snapshots and OpenCode stay manual-only. The retained file is always the recovery authority; its owner can inspect and copy it explicitly with `tap draft`.
A collapsed paste label does not contain the pasted bytes. Such backups keep the label verbatim and record `capture_status: incomplete` and `uncaptured_content: collapsed-paste` in their frontmatter. Ordinary clobber and explicit interrupt authority are unchanged. The owner notice and `tap draft` diagnostic say that pasted contents were not captured; they offer only the retained visible text, never a full restore.

Whitespace-only input (one blanking rule, part 2) earns no draft backup, flash, or restore. A readable blank full-composer snapshot supersedes an earlier nonblank prompt-line observation. The shared backup reader removes only the writer-added final newline; meaningful draft bytes, including their own trailing whitespace, are preserved. Unreadable backup/content decisions refuse before restore effects.

3. **Pre-clobber red cue, then clear (buffer-local only):** immediately before the clear, when the band holds real backed-up human input, the courier flashes the pane background red (best-effort, self-verifying the pane identity first) so the human sees a warning *before* their draft is cleared. Empty composers and queued-input holds have no arrival flash. The urgent path already flashes red before its interrupt; this covers the default direct-inject clobber that previously warned with nothing. Then bounded `C-u` plus `BSpace` drain cycles re-probe the full active input region between keys; a blank glyph line is not accepted while continuation lines remain, while Claude's bottom border, Cursor's empty dim placeholder box, and Codex terminal status chrome remain non-residue. The clear budget is the greater of sixteen cycles or twice the initial captured row count, capped at512; it never grows with newly arriving input. Each key settles for30ms before observation. Eight consecutive cycles with unchanged input stop the clear early. **Draft clearing only edits the input buffer; it never uses `Escape` or `C-c`.** Delivery is separate: Cursor plain delivery uses Enter+Enter, and Cursor interrupt delivery uses Ctrl+C before injection, as specified in the input-semantics table above.
4. **Pre-Enter sole-content gate (tap-maavp effect 2):** after a fresh inject lands and before the first Enter, the pre-Enter frame is classified again. Our id being visible is not the same as being alone: foreign bytes fused inside a readable bounded composer (the reader's `fused` flag) are the recipient's own typing, and Enter would submit them with the message. On the first fusion the shared clobber door backs up only the foreign bytes (the band with our exact wire removed), clears, and re-injects the sentinel once, re-verifying sole content before Enter; a second fusion stops unverified with the backup retained. The gate follows step 3's clear mechanics and never applies to a queue-prefix landing.
5. **Require an empty composer:** clearing stops as soon as the band is positively empty. The loop is bounded by captured rows and a hard ceiling. Persistent residue withholds the sentinel and reports the retained backup; human text is never knowingly submitted with the courier message.

6. **Plain-text restoration:** after a verified or harness-queued submit, restore complete plain text one line at a time using bracketed paste, never Enter. Recheck pane identity, the empty starting composer, and accumulated text after each line. Stop on interference, folding or unreadable output without corrective clearing. OpenCode and incomplete paste/image snapshots remain manual-only. A final exact comparison must verify the original bytes; unobservable trailing whitespace leaves restoration unverified. Keep every backup even when restoration succeeds.
7. **Owner notice on non-restoration paths (tap-cnka).** On the OpenCode skip, an incomplete paste/image snapshot, a paste-back that was attempted and missed, and an urgent interrupt whose Escape empties the composer (tap-u7ra7), TAP tells the **pane owner, at their own pane**, that the draft was saved and names `tap draft` as the recovery. This exists because the pre-existing guidance was written to **stderr**, which belongs to the *courier* process, i.e. the sender's terminal: the owner is a different human at a different pane and saw a red flash, a cleared draft, and nothing else. A backup nobody is told about is, experientially, a deletion.

   The notice is a `display-message`, **never an injection**: it writes to a client status line and never touches the input band, so it cannot clobber the draft it describes, recurse through the courier, or race the drain.

   **Targeting is explicit and is the part that is easy to get backwards.** `-t target-pane` selects only the *format context*; `-c target-client` selects who receives the message. TAP uses the session captured in that same backup-time record — not one resolved later, since a pane can be **moved between sessions** and a session read at notice time need not be the one the backed-up pane belonged to — lists that session's attached clients, and addresses each with `-c`. Passing `-t` alone delivers to the *invoking* client — the sender — which reproduces the very defect this notice exists to close, one level up.

   **Client cardinality is defined, not incidental.** *Many:* every client attached to the owner session is notified, because two humans watching one pane both saw the draft vanish and are both owed the recovery command. *Zero:* an unattended pane (the common crew-seat shape) has no status line; that is a deliberate best-effort no-op which MUST NOT fail the delivery path — a cosmetic notice can never be the thing that breaks a send. The zero-client case is where durable recovery is genuinely still missing (`tap-xz2t`), not a silent success.

   Duration is set **explicitly** to 8000ms rather than inheriting tmux's 4000ms default, because the reader just watched their own text vanish and is reacting rather than reading. The notice is **ephemeral by construction** and does not land in scrollback: it improves the odds at the moment of the event and is not a durable record. Identity is re-verified before writing, so a pane that died and was replaced is never told about a stranger's draft. That check carries a **server-generation stamp** captured in the SAME tmux record as the pane identity the backup was written for — one observation, at backup time, not a baseline minted later inside the notice — and compared at the effect boundary: a `%N` id is immutable only *within* one tmux server generation and ids recycle across them, so a restart recreating the same address and the same number would otherwise satisfy an id-only check. An unreadable generation fails closed — identity cannot be claimed without it, and refusing a cosmetic notice costs nothing next to telling a stranger.

   **Not every path that ends in a cleared band is covered, and the gap is named rather than implied.** The urgent-interrupt path (tap-u7ra7) closes one such gap: when the interrupt's `Escape` itself empties the composer, the clobber pipeline never runs and its backup would stay silent, so the owner notice fires after that submission finishes (verified or ended — never while the urgent payload is still in flight), worded incomplete when the backup says `capture_status: incomplete`; the urgent paste-collapse notice waits likewise (tap-xhb1l). The landed-check exit — `input did not land`, reached after the clobber has already backed up and cleared the band — still returns `5` without notifying. That leaves a live pane, an emptied band, a saved draft, and silence: the same experience this clause exists to remove, on a path it does not reach. Tracked as **tap-4fh3**; until it lands, the guarantee here is the five paths above and no more.
