Schedules live in `watch/reminders.json`, separately from `watch/arm.json`, and survive normal watch rearm and sidecar source re-exec. Scheduling with no watch creates a **reminders-only arm**: no `done_when`, evaluator, context notices, or silence probes. It uses the existing visible watcher sidecar, not a second daemon. Ordinary `watch on` still requires `done_when` and promotes a minimal arm to supervision while preserving schedules. Automatic supervision completion keeps scheduled reminders running in minimal mode; the minimal arm disarms once no scheduled occurrences remain. Explicit `watch off` refuses while scheduled reminders target another seat, naming their ids and targets. `--force` stops delivery and warns which scheduled reminders will not fire until re-armed; schedule state remains intact. The reminder queue lock covers the check, lease deletion and sidecar reap, so a concurrent schedule either participates in the decision or creates a fresh arm after shutdown. A later schedule or watch arm resumes delivery.

Scheduling confirms sidecar startup or reuse before printing `scheduled`, on the selected team's bus with its registry (a schedule made with `--team` names that team's runner, never the caller's cwd team's). An armed supervision watcher already dispatches reminders: a live recorded watcher PID (`watch-run.ts run`) with a positive heartbeat no older than three tick intervals (minimum 180 seconds) is reused without touching any window, and the receipt names its PID and armer. A future, absent, or stale heartbeat cannot establish this reuse. The arm identity is rechecked before reporting success. Session lookup prefers the arm owner's pane, then tries active registry panes until one resolves on the current tmux server. If no session resolves, the spawn lock times out, a foreign watch window blocks startup, or tmux fails to create a valid sidecar process, the command exits nonzero and names the stored reminder id with `no live reminder runner confirmed`, followed by `tap remind list` and `tap watch reminders --by <owner>` recovery guidance (with `--team`, the list remedy carries `--team <name>` and the watcher remedy binds that team's bus with an explicit `TAP_HOME=`, since `tap watch reminders` takes no team); the durable row remains inspectable. This is an observation failure, not a prediction that a running but unrecognized process cannot fire the reminder. `TAP_WATCH_NO_SPAWN=1` is the explicit spawn opt-out. Foreign windows remain untouched.

Delivery happens on the first tick at or after the due time. The next sleep shortens to the nearest deadline; a new reminder cannot interrupt a sleep in progress. An unreadable queue does not end the sidecar loop: each cycle the tick refuses it on one `tap watch:` line, the loop names the file and reason on another and sleeps the arm interval, and lease and heartbeat stay live until the queue reads again (`tap remind list` refuses the same queue). Repeats schedule from the dispatch tick, so missed intervals never burst. A queue lock serializes scheduling, cancellation, dispatch and minimal-arm completion; lease identity is checked before the send. A row whose `due_at` is not an integer (a hand edit) is neither a deadline nor dispatched; each tick announces it on one `tap watch: reminders:` line. Each occurrence persists a message id and `dispatching` state before each transport attempt. Successful or transport-pending sends count as handed off. Two refusals are rescheduled under a fresh message id, and a success clears the count. A refusal the sender declares repeatable (exit 1, next action `retry this command`; today only `reset_custody_busy`, raised before anything is placed) waits 5 s, 15 s, 30 s (tap-o31y6). A tmux outage refused before any effect (`server_unresponsive` with `effect: "none"`, see Structured failures) waits 30 s, 2 m, 10 m, 30 m, 60 m (tap-yk8it); without that field it is never re-attempted. One count spans a failure streak; the current refusal's schedule gives the wait and bound. Process loss leaves `dispatching`; other non-success exits, and a repeatable refusal after its last backoff, become `unresolved`. Both stay visible in `list` and are never retried automatically; inspect that occurrence's message first. On becoming `unresolved`, a plain (non-command) reminder sends its scheduling seat one best-effort notice with its `list` line, attempted once; its id and result stay on the row. Command-reminder occurrences keep their own circle-back accounting. Accepted one-shots keep their receipt state; acceptance is not recipient processing. This is a reminder service, not an exactly-once execution service for the body instructions.

### Team context census

`tap team` shows last reported input tokens and cap in its default human roster (for example, `145k / 380k`). Bound Codex JSONL telemetry supplies last-request input tokens (cached input is already included) and its reported window. Bound Claude assistant telemetry supplies input plus cache-read and cache-creation tokens. These are last-request observations, not cumulative billed usage or a prediction of the next request. These transcript reads are limited to the final 2 MiB of the registered transcript, validate session identity, skip records that measured no request, and invalidate usage after a compact boundary until new usage arrives. Unsupported or unavailable counts stay unknown; no transcript text is returned.

For Claude, use the readable running-process `CLAUDE_CODE_AUTO_COMPACT_WINDOW` as the displayed cap. When the variable is confirmed unset, default to 1M. Codex uses its session-reported window, defaulting to 1M when that field is absent. This 1M fallback is the operator-selected display default, labelled `default_1m` in JSON. An unreadable, invalid or contradictory override remains unknown; the human row shows the count alone. Percentages remain available in JSON, but are not rendered in the human roster. The configured window is not a claim about native model capacity or the exact automatic-compaction trigger; neither the current preset file nor a model-name guess is substituted.

OpenCode reads the registered session from its bound SQLite path, or `OPENCODE_DB_PATH` / the default `~/.local/share/opencode/opencode.db` when none is registered: the latest completed request's input plus cache-read and cache-write tokens, excluding output, reasoning and session totals. A summary boundary suppresses earlier usage until the next completed request; reverted sessions are unknown. The window comes from a per-directory `provider/model` map on disk. The roster only reads it; `tap team --refresh-models` refetches each session directory with `--pure`, and launching a seat with `--model` records that model. Entries from an older OpenCode or past seven days are rebuilt. A missing window shows `<count> / ?` and a footer naming the fix; JSON stays `window_tokens: null`. Plugin-supplied limits and process-only environment overrides are not observed; invalid limits never yield a guessed cap. Schema changes or missing session bindings leave usage unknown.

JSON adds `context_tokens`, with `input_tokens`, `observed_at` (usage event time), `source`, `window_tokens`, `window_source`, `used_percent`, `percent_source`, and `unknown_reason`. Unknown is null; `context_unknown_reason` says why (`not_sampled` if unread). The same tail read yields observed model/effort as top-level `observed_*` keys, never inside `context_tokens`. Token sources are `codex_transcript`, `claude_transcript`, and `opencode_store`; percentage sources are `codex_reported_window`, `claude_process_env`, `default_1m`, `opencode_model`, and the retained `footer`. Existing footer fields keep their meaning. JSON adds `context_used_percent`, `context_source` (`footer` or null), and `sampled_at` (capture time or null). A footer percentage uses the harness's own denominator; it is not a normalized model capacity or auto-compact limit, and capture time does not establish when the harness measured its usage. `tap team --context` remains supported without a deprecation warning; `--context --json` also retains `last_outbound_age_seconds` and `pending_inbound_ask`. Last outbound age is message activity, not idle time. The default command does not scan message queues. Context extraction reuses the existing native agent-state capture; no pane transcript is returned.

The gauge reader is shared with the watcher's context-pressure notice. Only name-proven active panes with supported gauges are read; the census capture uses the resolved pane id and checks the tmux generation around the read. Missing, unsupported, or unavailable gauges remain null (`?` in text), never zero. Pending-ask status uses the same canonical, parked and indexed sender-bus census as watcher admission; unclassifiable data is null rather than clear. Outbound age uses the existing supervision reader and clamps future timestamps to now; no observed outbound is null. These are observations for the leader's decision, not authorization to compact or clear a teammate with unfinished work.

### Context-pressure notice (between tasks)

Each armed watch tick can send a `kind: progress`, settle-only `--wake` note to an idle seat with context usage at or above `--context-threshold` (default 40, range 1..100). `--context-exempt h1,h2` excludes named seats such as lane drivers. Both settings belong to the arm record and follow the existing explicit-intent rearm rules; an omitted flag does not change a running watch.

The watcher accepts footer gauges from Claude and opencode (`NNNK (NN%)` used, plus Claude Bar `NN% (TOKENS) ctx`) and Codex (`Context NN% left`, converted to usage). Unsupported, ambiguous, or missing gauges do not trigger a notice. The seat must be positively idle, and no unsettled inbound ask may exist in canonical or parked payloads, including indexed foreign sender buses. Unreadable queue state suppresses the notice. The idle and lease checks are repeated before sending.

The notice asks the recipient to recheck unfinished work and new asks before clearing (`/clear` for Claude and Codex, `/new` for opencode), preserve any standing brief, then check registration and run `tap in` only if offline. The watcher never submits a clear command. One notice is retained per seat/pane pressure episode; usage below threshold re-arms it. A failed send is not latched. As with progress notes, this supervision traffic does not advance the work-activity clock or count as unfinished work. The wake bypasses recipient digest windows. This pass runs independently of the silence ladder and shares the sidecar's identity and source-refresh boundaries.

### Context-freeze advisory (Codex, empty-inbox stall)

The livelock advisory above only fires when an unsettled inbound *exists*, so a wait-dependent stall with an **empty inbox** never triggers it. The context-freeze advisory closes that blind spot by reading the stall directly. Each tick, an armed `tap watch` parses the Codex `Working (<elapsed> … esc to interrupt)` timer and hashes the pane **with that animated Working line removed** — the retained body still carries the `Context <n>% left` burn row and the scrollback. When the body hash stays byte-stable while the parsed timer **strictly advances** for at least `TAP_WATCH_FREEZE_SECONDS` (default 300), watch sends one advisory `notice` to the armer for that seat. It consults no inbound payload at all — an empty inbox is expected. It never auto-interrupts. A body-hash change re-baselines the seat (real progress) and re-arms one advisory for the next episode; a fully-frozen pane whose timer *also* stopped is excluded (not advancing — that is a dead pane, not a live wait-stall), as is a seat with no live `Working` timer. One advisory per freeze episode (a `fired` latch, cleared on re-baseline or re-arm).
