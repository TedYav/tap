A longer digit string is UNREADABLE and resolves LIVE; it is never a positive mismatch, because a value none of the three can read says nothing about which boot or which process wrote it. The EPOCH bound is a digit COUNT rather than a range check on purpose — the pid's is the range, as above — because the shell does not report arithmetic overflow, it wraps silently to a plausible finite number, so "did the conversion succeed" is answerable in two implementations and not the third, while string length is decided identically in all of them. It bounds representability rather than plausible dates — policing the calendar would be a separate policy the three would have to agree on. **A JSON number means one thing in every implementation, and it governs every numeric factor.** JSON has no integer type, so a value written as `1e5` or `99999999.0` reaches JavaScript and Python as the same float and renders differently in each; a number is readable if and only if it is integral, rendered canonically without exponent or fractional part, and a fractional value is unreadable rather than truncated. The rule applies to the recorded **pid** and to the recorded **start fingerprint** alike, and each factor keeps its own shape gate afterwards: a pid must be a positive integer, while a fingerprint is any non-negative one. **Canonicalization happens before a factor is tested for absence, not after.** Zero is falsy in both languages, so a fingerprint recorded as the number `0` was read as a MISSING factor and resolved LIVE in the two readers while the reset-acquire path compared it and proved the fence stale — one fence, opposite answers, from a guard that never asked the question it appeared to. "The factor is absent" and "the factor is the number zero" are different questions, and the second one is answerable: `0` is a legitimate fingerprint value that simply matches no live process, exactly as the string `"0"` always did.
