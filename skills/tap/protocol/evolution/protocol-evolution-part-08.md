Under `shutdown`, whose policy deletes the acting registry, the caller's rows are captured INSIDE the same locked transaction that deletes them and are RESTORED under the registry lock on every survivor outcome, so a refused or failed self-kill never leaves a live seat without a registry row. That capture is FAIL-CLOSED: if the rows cannot be captured the clear does not proceed, because deleting without recovery state is precisely the failure the capture exists to prevent. Restoration rebuilds a deleted registry from the captured envelope — team metadata and the original seat axis, since a provenance-empty envelope is itself data loss and moving a `seats`-keyed registry onto the `agents` axis is its own corruption — preserves a registry that is present but unreadable rather than overwriting it, and RETAINS its recovery state when it cannot complete, reporting a loud partial outcome rather than a silent one. A missing registry means "no rows, hence no co-tenant" only under `clear`, which deletes it deliberately; under `down` a vanished registry fails closed, because reading it as an empty roster would conclude there is nothing to protect and kill. The recovery artifact is OPERATION-UNIQUE and lives under `$TAP_HOME/recovery/`: a run never deletes an artifact it did not create, so a retry or a concurrent seat's shutdown cannot destroy evidence another run still needs. It is removed only once RESOLVED — the restore succeeded, or it never held rows — and a killed transaction's staged `.inflight` copy is reaped on the same rule wherever the process survives to do so. On a REAL successful self-kill it is not: the caller is destroyed by its own kill, so nothing runs afterwards to reap, and the row-bearing `.inflight` copy REMAINS under `$TAP_HOME/recovery/`. That is stated rather than fixed here, and inventing a post-death cleanup owner is a larger change than this one. It is inert in the ordinary case — a full clear takes the whole registry with the team, so there is nothing left for the copy to conflict with — but NOT unconditionally: under a partial clear (`--keep-self`, or seats retained by `--except`/`--only`) the filtered registry stays LIVE while the dead caller's row sits in the `.inflight` copy, so a future repair owner must not reinsert that row into a registry whose remaining seats are alive. Nothing enumerates the directory automatically; an operator listing `$TAP_HOME/recovery/` will find it, and no verb — `tap doctor` included — reports it today. When a survivor cannot restore, `down|shutdown --json` carries `recovery_pending: true`, `recovery_path` (the retained artifact) and `recovery_hint`; **Per-seat events and the self-kill boundary.** A seat the LOCKED transaction adopts — a row that registered after planning and is a co-tenant of a session this run kills — gets a durable `killed` event like any planned seat, drained before the self-last kill so it is on disk while a writer still exists. There is ONE exception, and it is structural rather than an omission: a row adopted by the SELF-LAST transaction gets no pre-kill terminal event. During down preparation and self-last late adoption, a crew row is named in the session's nonterminal `kill-requested` detail (`crew=<handle>,<handle>`) before its deletion is published. Prepare and late adoption may each append a request as new rows become known; request count is not a completion count. An append failure refuses before crew deletion, and a surviving failed self-kill restores rows before `crew_restored`. A terminal crew event is written only by a writer that survives the fact it records. What the log carries instead is the caller's own `kill-requested` for that SESSION, and the record is session-granular, so it covers the co-tenant exactly as it covers the caller. The cost for a non-crew row is named: HANDLE identity is lost for that seat — a reader learns the session was requested-killed, not which non-crew seats went with it; crew handles remain named in the request detail. The guarantee that holds regardless is that no seat is ever recorded `killed` before its kill is proven; the per-seat bridge is written only at proven-stopped exits, so a transaction that adopts and then refuses or fails claims nothing. **Adoption is decided by the live authorizer, never by the row's own stamp:** every candidate late row passes the same membership check a plan-time row does, under the same lock, so a row whose stored `session` still names the target while its pane has moved elsewhere is left untouched rather than stripped and suspended — a stamp records where a seat WAS, and killing a session on that evidence leaves a live pane holding an unreachable row. **What the record IS depends on the policy:** under `down` an adopted non-crew row is stamped `suspended`/`session_stopped`, while crew rows are deleted under both `down` and `shutdown`; under `shutdown`, whose contract deletes the acting registry, the truthful record of a stopped row is its DELETION, and when nothing survives that deletion the registry file goes with it — a suspended row would leave an acting registry standing that the verb promises to remove, on a path where the file exists only because that seat re-registered after the clear. The same site re-stamps a plan-time row that was re-activated during the receipt interval: its kill WARRANT is still decided once, but its STATE is re-read before the deferred kill, so a row restored to `active` in that window does not survive its own session. **A row adopted into a session whose kill is then REFUSED is retained by the clear, not deleted** — it belongs to a session that is still alive and appears in no plan-time map, so it is reported on its own channel (distinct from the proven-stopped one, which must keep claiming only terminal facts) and joins the keep set for that session. Finally, the buffers these records travel in are allocated BEFORE the first kill and their allocation failure is a refusal (`recovery_unavailable`), not a silent downgrade: continuing without them would stop seats that no durable record could name, and refusing costs nothing at a point where nothing has been mutated.

the durable log gains a `recovery-pending` event beside the terminal `kill-refused`/`kill-failed` — best-effort, because the event log lives in the bus home, so when the bus itself is what failed (an unwritable `$TAP_HOME`) the append cannot succeed and the aggregate plus the exit code carry the disclosure alone; and the command EXITS NONZERO after those receipts, so a supervisor reading only the exit code is not told a partial run succeeded. No repair verb is named in that payload, because none exists yet — a next-step that cannot run from the failure state is worse than none. A failure to create or capture recovery state is itself `error_class=recovery_unavailable` and obeys the JSON failure contract (one `ok:false` object on stdout, nothing on stderr): the registry is retained, the caller is not killed, and any teammate sessions already stopped are named in the detail.
