**Team-lifecycle selection (`--only`, tap-sttl):** the same five verbs accept `--only <h1,h2,...>` — act on the named seats and spare everything else. It is the exact complement of `--except` in MEANING, and deliberately NOT in implementation: the complement is never precomputed. The value goes through the same tokenizer, the same charset and team-local rules, and the same roster gate, and is then carried as a POSITIVE set. Each verb asks "is this seat spared?" per row, at plan time, against the very snapshot it is about to act on — `lib.sh` `tap_seat_spared` in bash, the same rule spelled inline in each Python planner. Under `--only` the exclusion set is EMPTY by construction, so any consumer still reading it directly gets an honest empty answer rather than a complement that looks authoritative, and `tap_select_any` (not `tap_except_any`) is the predicate for "was a selection given at all". Resolving a complement at parse time was the FIRST design and is retired: it froze an answer derived from one registry read while every verb re-reads later to plan, so a seat registering in that window was absent from the frozen set and was acted on though the operator never named it. The polarity is why the same shape was safe for `--except`, which correctly acts on a late-registering seat, and unsafe for `--only`, which must spare it. Every error class is identical to `--except` (`usage_error` for a qualified form, an empty value, an empty element between commas, or no operand; `not_found` for a handle no seat answers to, naming the unmatched handles and the live roster), with refusals naming `--only` rather than the flag the operator did not type. An empty or unreadable roster therefore refuses at the gate rather than resolving to "spare nobody". `--only` and `--except` together are `usage_error`: they are complements, so naming both states the selection twice and the two statements can disagree. `tap team detach --handle` and `--only` likewise refuse together, because both state the selection and the two statements can disagree. They are NOT the same operation and this sentence used to say they were (found in review): `--only` is a SELECTION and therefore session-granular like every other selector — a seat it does not name is spared, and sparing spares that seat's whole tmux session — while `--handle` targets one ROW and detaches its session regardless of who else occupies it. On a session shared by `a` and `b`, `detach --only a` spares the session (because `b` is not named) and `detach --handle a` detaches it. The divergence is the session-granular rule doing its job, not a gap: making `--only a` detach that session would disconnect `b`'s clients, which the operator did not select. `--handle` keeps its row-targeted meaning because it is an existing flag whose semantics this change does not get to redefine. Naming the entire roster is legal and means "act on everyone"; nothing is spared, which is why every verb's selector receipt keys on the flag the operator typed rather than on whether a spared set is nonempty — otherwise a whole-team run would print no trace of the selector and read as unselected. TEXT receipts name `--only` and report the TYPED selection — a rule about RECEIPTS (the "spared N seat(s) by ..." summary and the no-seats-matched line), not about the dry-run PLAN, which enumerates the rows on both sides by design and marks the spared side "the complement — not a typed set" so it cannot be read as the operator's input. A plan is a pre-execution disclosure whose whole purpose is naming what will and will not be touched, and suppressing the spared side would delete that safety property on the more dangerous flag. The live `down|shutdown` receipt keeps that typed selector in front and ends with `(spared: h1, h2, ...)`, the effective spared handles (session co-tenants, `--keep-self`, late registrations), drawn from the same list as the count so a counted seat is always named; the tail is omitted only when a typed `--except` list already equals that set. Machine surfaces carry the EFFECTIVE spared set: `down|shutdown --json` `excluded_handles[]`, and `tap team up`'s all-spared aggregate (`excluded[]` plus its companion stderr line), report the seats actually spared, because a consumer of those fields reconciles against real sessions rather than reading intent; `detach`'s per-row `excluded` labels are effective-set for the same reason. That effective set is accumulated from the rows during planning AND completed under the locked clear, which folds in any row it spared that planning never saw — so the receipt names seats the plan could not have known about. Planning alone was the original mechanism and is no longer the whole of it. Sparing is session-granular, so a spared seat's tmux session must be KNOWN before any verb acts. Three cases, decided at PLANNING on `down|shutdown|detach`: a pane-less (`delivery: poll`) spared seat contributes NO session, because nothing occupies one and synthesizing `<team>/<handle>` could collide with a real noncanonical session belonging to a SELECTED seat; a spared pane row with a `session` stamp contributes it; and a spared PANE row WITHOUT a stamp is handled differently by verb. On `down|shutdown` it is now POSITIVELY OBSERVED (panel review, P1-a; supersedes the two options rejected here previously). Such a row is reachable — registration writes `session` only when its tmux probe succeeds — and the two prior answers were both rejected: guessing `<team>/<handle>` risks sparing the wrong session outright, while contributing nothing left a known gap where a pane that really occupies a SELECTED seat's session kept that session actionable, silently un-sparing a co-tenant the operator named. The fix asks tmux directly for the row's CURRENT session (`tap_pane_observe`, not the stored/stale value) and uses that; if the observation itself fails, the run refuses the WHOLE destructive selection as `error_class=unobservable_spare` rather than guess or proceed with the gap. This observation is skipped when the operator's own selection already spares every seat — nothing is left that could be destroyed either way, so an unobservable co-tenant pane in that case does not cost the pre-existing all-spared legal no-op (see above). `detach`'s own planner still takes the OLDER "contributes none" answer for this row shape — a deliberate, tracked gap (thread 29), not an oversight the down|shutdown fix silently closed too: a run-level refusal there was implemented and reverted as a larger change than the finding priced, and it remains open. Do not read the down|shutdown fix as covering detach's planner; it does not.

`detach`'s plan-to-effect window is a SEPARATE property from the above, and IS closed (tap-sttl, P1-b; panel review): the plan is built from one registry read, then each session is acted on later in a loop, so a co-tenant that registers into a session AFTER that read and BEFORE detach reaches it was invisible to the plan and got detached along with everyone else. Each session detach acts on now re-reads the registry under `registry.lock`, held through the `has-session`/`list-clients`/`detach-client` calls themselves (not released before the effect — a half-applied re-check that dropped the lock first would look identical and close nothing), immediately before acting; a co-tenant found live in that session at re-check time excludes it rather than detaching it, named in the receipt as a late exclusion distinct from a plan-time one. `--only` composes with `--keep-self` exactly as `--except` does — the spared set is their UNION and keep-self wins where they disagree, so `tap team down --only <caller> --keep-self` spares the caller and acts on nothing; the receipt fallback counts that union rather than selector exclusions alone, so a run cannot announce "none spared" while keep-self spared a seat. Selection is keyed on the CANONICAL roster handle everywhere: consumers read the `handle` field (see `session list --json`) and never re-derive one from a session name, since a noncanonical session name or an index>1 seat yields a different string and a mis-keyed handle silently matches nothing — sparing under `--except` a seat that then gets acted on, and under `--only` acting on a seat never named. On `up` the positive set travels to the launcher and is applied against the manifest records it would actually resume, because a record's registry tag is optional and a registry-derived answer could miss such a record entirely. One consequence is worth naming: an unrostered manifest record can be SPARED by `--only` but never TARGETED by it, since naming it would not survive the registry-backed roster gate. That is deliberate — typo protection outranks reaching a rowless record, and it is the safe direction of the two.
