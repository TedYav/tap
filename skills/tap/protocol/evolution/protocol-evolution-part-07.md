**`tap team up` resumes the whole cohort — one seat's failure is not the cohort's (tap-7r3fn.23):** `resume --all` attempts every selected seat; a per-seat failure (nonzero resume exit, a tmux `CalledProcessError` such as respawn-pane ENXIO, or a per-seat `LauncherError` such as "harness did not start") rolls back that seat's own launch transaction (`suspended`/`repair_failed`, unchanged) and the verb moves on to the rest of the cohort. After the per-record stream a terminal summary names every failed seat WITH its reason (`resume failed (exit N)` / `tmux error: <argv summary>` / the `LauncherError` text). Text mode prints each failed seat's manual command (`tap session resume <harness> <handle>`); an interactive caller (TTY, non-dry-run, non-`--json`) is offered ONE `start a new session and resume manually?` prompt — Y relaunches each listed seat fresh under its own canonical name through the collision chooser's [k] fresh path (backup-before-stop, `kill_backup_required` replacement authority for the exact session name, never the chooser itself), N leaves the seats as they are. `--json` never prompts and ends the per-record stream with one terminal object `{"ok": false, "resumed": N, "total": M, "failed": [{"handle", "session", "reason"}]}` — the only aggregate after the stream besides the all-spared case. Exit is a cohort verdict: `0` when every selected seat came up (a successful accepted fresh start counts) and a flat `1` from the ordinary failure summary when any seat failed, including when a fresh launch fails — a seat's own launch exit code never becomes the run's exit (tap-4uijo); `--json` and the per-seat warning line carry the seat detail. Seats retained at a startup dialog (`manual_attention`, exit `2`), fatal refusals and interrupts keep their own documented codes. Interrupts and any unanticipated error — anything that is neither a `CalledProcessError` nor a per-seat `LauncherError` — still abort the run; the catch set is deliberately narrow. The fresh path is one extracted callable (`execute_fresh_launch`) shared by `session launch`'s chooser, the fresh-start arm, and `session resume`'s create-fallback (tap-7r3fn.24).

**Self-kill authorization and caller-row recovery (tap-sttl).** A lifecycle verb's own session is killed LAST, after its receipt, and that kill takes the same locked authorization every other session takes: the co-tenant set is re-read from the registry under `registry.lock`, and the kill happens inside that same critical section, so no seat can join the caller's session between the decision and the effect. Three outcomes are DISTINCT and reported as such — `killed`, `refused` (an unselected seat shares the session, or the warrant no longer holds), and `kill-failed` (authorized, attempted, session survived). A refusal and a failed kill are never collapsed, because they need different durable records and different recovery: a refusal emits `kill-refused` and a failed kill emits `kill-failed`, each terminal against the preceding `kill-requested`, so a supervisor reading the event log can tell the three apart. When the caller SURVIVES a run whose receipt already announced `pending_self_kill`, the machine record is CORRECTED — a further `--json` aggregate (or its text equivalent) retracts the pending kill and lists the session as refused. The session warrant itself is decided once, at plan time: an epoch flip does not invalidate a name-keyed self warrant, so what the final lock re-examines is the co-tenant set, which is the thing the receipt interval can actually change. **A teammate's `kill-failed` is durable too (tap-sttl, P2; panel review):** the same authorized-and-attempted-but-survived outcome, for a non-self session, appends `action=kill-failed` to `registry-events.log` exactly as self's does — previously only a transient `tap_warning`, so a supervisor reading the event log could not distinguish a teammate's survived kill from one never attempted. **A re-activated caller row is only touched if it still occupies the session being killed (gate review):** the caller's `prepare`-suspended row can be reactivated during the receipt interval by two different events — the SAME pane re-registering (its row belongs to the dying session, and gets restamped/deleted with it), or a REPLACEMENT pane taking over the handle into a genuinely different, still-live session (its row does not belong to the session being killed at all). Only the session-matching case is stamped; a replacement's row is left exactly alone, because touching it would strip or delete the only row a live, reachable seat depends on while its actual session keeps running untouched underneath.
