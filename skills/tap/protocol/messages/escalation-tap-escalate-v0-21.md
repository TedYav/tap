## Escalation (`tap escalate`) (v0.21)

`tap escalate [--from <me>] [--team <name>] [--urgent] [--json] -f <path>` asks the configured notifier to alert **the human directly**. Write the question to a file first, then pass `-f <path>`. Alternative: `-f - <<'EOF'` with a quoted delimiter. `-m "<question>"` remains available for short shell-safe text. The verb composes a one-line label from the caller's TAP identity. It creates no bus payload, receipt, or reply obligation.

The default `system` notifier uses macOS `osascript` or Linux `notify-send`. macOS requires the terminal app's notification permission; Linux requires a desktop notification service/session. Acceptance cannot prove display or human receipt. Unsupported platforms and missing executables refuse actionably. Use a configured command for a phone or remote service.

**Why direct.** Through v0.20 this verb was address indirection over `tap send`: it resolved a configured gateway seat and sent it `kind=escalate`. That routed the human's question through another AGENT, which had to be alive, notice, and relay it. The premise of escalating is that the human may be AWAY — so the one hop that must not depend on a live local seat was exactly the hop that did. The gateway path is **retired, not deprecated**: `~/.tap/escalation.json`, `TAP_ESCALATION_TARGET`, and the `kind=escalate` send are gone from this verb, and nothing may be built against gateway arrivals.

`--kind escalate` remains a user-settable envelope value on `tap send`, with its unchanged courier semantics (pre-claim digest carve-out, urgent default, §Spool). That is generic courier behavior for anyone passing the flag — **not** escalation routing.

**Label composition.** `<question> — <team>/<handle>`, with a differing tmux session appended as described below. The question comes first so a truncated preview retains it. The built-in urgent title starts with 🚨; Linux also receives critical urgency. Command adapters receive urgency as `routine` or `urgent`. Built-in and legacy argv place `--` before user text; a custom command's template owns its option terminator.

**The question is the FIRST NON-EMPTY LINE of the body** (`-m` or `-f`); the remainder is local depth that never leaves the machine. There is no `--summary` flag. `--preview` is accepted for composing consistency but has no effect on this notifier-only verb; it neither replaces the question nor creates a TAP payload. The shell-body guard scans `--preview` for backticks and `$()` before shell expansion, just as it scans `-m` (tap-9sjp / tap-psif). Prefer `-f` with a **quoted** heredoc whenever the question quotes commands. A body with no non-empty line is refused (`error_class=empty_question`) rather than sending a bare seat label.

**Identity comes from the resolved `--from`, never a fresh `tap whoami`.** The watch layer and goalie escalate `--from` the ARMER while running pane-less themselves; re-deriving identity inside the verb would relabel the alert with the invoking process instead of the seat that owns the run.

**Session precision.** The requirement is the tmux session the human can attach to. For launcher-managed seats the session IS `<team>/<handle>`, so the common label is already exact. When the registry's authoritative pane-backed entry records a DIFFERENT session, it is appended as `[tmux: <session>]`. An unreadable session yields **no suffix** — absence of observation is not observation of absence, and a guessed address is worse than none. `delivery: poll` seats have no pane and no session: no suffix, explicitly one-way.

**`--from` validation is about TRUTHFULNESS, not dischargeability.** The v0.20 bar was `tap_registry_dischargeable`, justified by "the reply obligation must land somewhere" (§Reply routing). With no bus send there is no reply obligation, so that rationale is void and inheriting the check would leave a guard true only by coincidence. The surviving reason is weaker: the label must name a seat the human can actually attach to. An **unregistered** `--from` is refused (`error_class=unregistered_from`) because it would put a fictional address on the human's phone. A registered but **suspended, pane-gone, or poll** seat PROCEEDS, one-way — "the seat that asked is no longer reachable" is precisely a state a human should be told about, not one that should silence the alarm. This is a deliberate widening: a pane-gone armer can now reach the human, where v0.20 refused it.

**`--team` anchors the bus for a pane-less caller** (§Bus anchor for pane-less callers), applied FIRST via `tap_apply_team_override` — the registry reads below are what it redirects.

**Priority is the caller's judgment, not a rationed resource.** Two priorities: normal (default) and `--urgent`, which renders `🚨` first and means drop-everything. The verb documents the SITUATIONS urgent fits — a hard blocker parking a lane, a critical or hard-to-reverse decision about to be made on doubt, anything where waiting produces a worse outcome than interrupting — and leaves the pick to the agent. There is deliberately no sparingly-rule: the stated preference is *"I prefer escalations rather than bad decisions or blockers"*, so the failure mode being designed against is a silent blocker or a guessed fork, not an over-eager notification.

**Robustness of the notifier call.** One shared native module owns config resolution and process-group execution for escalation and goalie heartbeat. Stdin is closed, child stdout/stderr go to stderr, and the caller environment is inherited except internal `BUN_BE_BUN`. The deadline defaults to 20 seconds; `notifications.timeout_seconds` accepts integers from 1 through 2147483, and `TAP_NOTIFY_TIMEOUT_SECONDS` explicitly overrides it. A deadline or caller cancellation kills the owned process group, including resistant descendants. An actual deadline produces `notify_timeout`; child exit 143 and caller SIGTERM are separate `notify_failed` outcomes. Neither failure nor timeout triggers a retry or another transport. NUL in transport title/body becomes literal `\0` before spawning. The question reader strips CR before choosing the first nonempty line.

**A reservation is not a seat.** A `--from` row with `status=pending` or `status_reason=launching` is refused (`error_class=reserved_from`): it names something that has never been routable. This does not narrow the widening above — suspended, pane-gone, and poll seats still escalate one-way, because they WERE real and their unreachability is itself news.

**Configuration and precedence.** `TAP_NOTIFY_USER_BIN` (legacy argv override) > `[notifications]` in `${XDG_CONFIG_HOME:-$HOME/.config}/tap/config.toml` > built-in `system`. The override exists for emergency routing and test isolation, not a parallel normal configuration surface. TAP no longer discovers `notify-user` automatically. Both isolated runners still unconditionally pin this override to a nonexistent executable, so unstubbed tests fail instead of contacting the operator. System-transport tests explicitly stub both `osascript` and `notify-send`.

`notifications.notifier` is `system` or `command`. For `command`, `notifications.command` is a nonempty TOML string array whose first token is the executable. Whole-token `{title}`, `{body}`, and `{urgency}` placeholders are replaced once; all other arguments remain literal. Unknown or embedded placeholders, NUL arguments, malformed configuration, and invalid deadlines refuse before execution. No shell is involved. Set the command array with `tap config set notifications.command '<TOML array>'` before selecting `notifications.notifier command`; the existing locked config editor preserves unrelated content. `tap doctor` reports selection, executable availability, and platform limitations without invoking it.

**Producers.** A blocked agent invokes this verb; watch invokes it as its armer after publishing the sticky NOTIFY record. Watch's publication, ack, and episode policy remain intact, but its unconditional second `osascript` leg is removed: only the selected transport may run. Standalone goalie heartbeat also uses the shared transport, retaining its existing recurrence policy. Watcher bodies describe their own condition rather than an agent's private escalation depth.

**No reply routing.** There is no payload to reply to and no `tap outstanding` entry. The human answers by attaching to the named session and typing in that pane — which is the point of carrying the seat label. A caller that needs a durable, settleable obligation should use `tap send`, not this verb.

**Exit codes and evidence.** `0` means notifier acceptance, not human receipt; JSON retains `notified: true` and adds `delivery: "accepted"`, `human_received: null`. Human output states that receipt is unconfirmed. `1` covers usage, identity/body refusals, and `notify_config_invalid`. `2` with `notify_user_missing` means no executable was available and no notification was attempted; `2` with `notify_timeout` means delivery is unknown. Other nonzero notifier exits or cancellation use `notify_failed` and retain their status; delivery remains unconfirmed. Spawn failure reports no attempted notification. There is exactly one attempt per invocation, with no fallback even after a nonzero exit.
