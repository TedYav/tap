- **`tap reply <id>` routes the answer to `reply_to` when present, `from` otherwise** — the recipient's own muscle memory (`tap reply <id> -f <path>`, or `-f - <<'EOF'`) never changes; the courier is the one reading the payload frontmatter and choosing the target. New `reply_to` values are already sender-team-qualified at the original send, so a cross-team recipient cannot reinterpret a same-named bare handle locally. A pre-upgrade payload can still carry a bare `reply_to`; on a foreign inbound (`from_team` set and different from the replying seat's team) `tap reply` never resolves it against the local registry and takes the ordinary warning and original-sender fallback instead (tap-bgxp). The qualified value becomes an ordinary cross-worktree `TO` with no special-casing. An explicit `--reply-to` passed to `tap reply` itself stamps THAT OUTBOUND's own `reply_to` field — a next-hop pointer for whoever eventually answers this reply — it does NOT change who this reply is delivered to; the delivery target (`TARGET`) stays governed by the inbound's own `reply_to`/`from` resolution above, unchanged by `tap reply`'s own `--reply-to` flag.
- **Deliverable, not merely known — re-checked at reply time, not trusted from send time (panel MUST-FIX 1).** `reply_to` must name a seat `tap_seat_deliverable` accepts — an active pane-backed member or an active poll member, the SAME bar `--from` itself requires — at BOTH send time and reply time, never mere registry existence. A pending/suspended target is not deliverable: accepting it at send time and only discovering that at reply time would route-then-fail (delivery itself refusing `seat_pending`/`suspended`) with the inbound left unsettled, which the deliverability bar makes structurally unreachable. The seat `reply_to` names may still have gone non-deliverable BETWEEN the original send and the eventual reply (left the team, its team un-enrolled) — `tap reply` re-resolves it before routing; **an undeliverable `reply_to` falls back to `from` with a stderr note.** That fallback itself never fails, but "falls back to `from`" and "the reply as a whole cannot fail" are different claims: the FALLBACK TARGET can still be refused by the ordinary unattended-sender rule below (sol's both-targets-gone case) — the refusal names `tap read <id>` for inspection or `tap reply <id> --allow-unattended -f <file>` for a problem report, so this is never a silent dead end, but it is not an unconditional "never a hard failure."
- **Settlement is UNCHANGED and stays orthogonal to routing.** `.done` discharges the **sender's** (`from`'s) obligation — `tap outstanding` keys off `from`, exactly as before — `reply_to` only redirects where the ANSWER text lands, never who is credited with having been answered.
- **Different local seat, enforced (tap-tdz).** An explicit `tap send --reply-to` that normalizes to the sender's own local handle refuses, and `tap register --reply-to` refuses storing that self-reference once the seat exists. A pre-existing registry-derived self default instead follows stale-auto-stamp behavior: warn, omit the stamp, and send; the omission cannot grant `reply=expected`. A same-named handle on another team remains a distinct, legal principal. This prevents an unattended seat from granting itself the reply channel that only a durable principal may own without bricking a raced or legacy automation seat.
- **Unattended-refusal interacts with routing, not with the original sender.** §Reply expectation's unattended-sender refusal exists to stop an accidental ack-loop into a seat that can't hear it. Routing via a deliverable `reply_to` targets a DIFFERENT, already-proven-deliverable seat by construction — the original sender's `unattended` flag never applies to a message that never goes to them, so the refusal does not fire. Replying **directly** to an unattended sender (no `reply_to` present, or `reply_to` fell back to `from`) still refuses without `--allow-unattended`, unchanged.
- **The unattended contradiction, resolved (panel MUST-FIX 4).** The advertised cron/sweep use case could not previously produce an ordinary `reply=expected` send: `--unattended` forces `settle-only`, and a poll-mode seat's own default instructs `tap read` for notes — the prohibitive rule's premise is "the sender cannot consume a reply," which is sound for a bare unattended seat. That premise no longer holds once a validated deliverable `reply_to` owns the response channel: **an unattended sender WITH a validated deliverable `reply_to` MAY stamp `reply=expected` by passing `--ask` (aliases `--reply`, `--expect-reply`)** (mere presence of a registered `reply_to` does not by itself flip the default — the opt-in flag is still required, symmetric with the existing poll-mode carve-out above). The grant transfers the reply-expectation to the durable principal, not to the unattended seat itself.
- **Composition with `--unattended`:** `tap register --unattended --reply-to <handle|team/handle>` stores the address on the seat; every subsequent plain `tap send --from <that-seat>` auto-stamps `reply_to` from the registration (no need to repeat `--reply-to` on every send) — UNLESS that stamped value has gone non-deliverable, in which case the send soft-fails the stamp (warn, omit, send anyway) rather than dying, so the seat the feature exists for is never bricked by its principal moving on (MUST-FIX 3; an EXPLICIT `--reply-to` on an individual send still keeps the hard refusal — typo discipline — and still wins over the seat's stored default).
- **Replier contamination, prevented (panel MUST-FIX 2).** `tap reply` shells out to `tap send` to compose its outbound; without a suppression, that outbound would auto-stamp the ACTOR's own registered `reply_to` (`register --unattended --reply-to`) — a courier-composed reply is not an ordinary send the actor chose to make, so the actor's own follow-up channel must never silently ride onto someone else's reply (this would misroute a durable principal's follow-up to the ACTOR's principal instead of the actor). Bash `tap reply` always passes `--no-auto-reply-to` (internal) to `tap send` to suppress the registry-derived default; native nested send uses an equivalent internal suppression rather than that Bash-owned flag. An explicit `--reply-to` passed to `tap reply` itself remains allowed and is passed through.
- **Poll display (SMALLER 5).** `tap poll`'s payload-derived display surfaces `reply_to=<address>` when present (text and `--json`), so a pane member sees a payload's reply might route elsewhere before answering. Poll-only — the sentinel wire format is unchanged (the panel's reconciled ruling: the sentinel stays the zero-authority routing poke it always was; `reply_to` is a courier-payload fact, not a sentinel fact).
