## Reply expectation (v0.3)

Every send carries a sender-declared reply expectation so the recipient's obligation is **mechanically decidable**, never inferred (the design target is non-frontier agents completing the loop without judgment):

- **`reply: expected`** — the recipient should answer (via `tap reply`); the answer settles the inbound payload.
- **`reply: settle-only`** — no answer is wanted; the recipient reads the body and settles with `tap read` without sending a separate acknowledgment. An ordinary settle-only message carries no directive (that is a SENDER contract — see `/tap`'s liveness floor, and the order-shape guard below, which refuses order-shaped notes at send time); the supervision kinds `probe` and `notice` are the defined exception, and work that arrives despite the floor is still work — settling never cancels it. Settlement *is* the acknowledgment — **do not send a got-it/ack payload.** `tap reply` is only appropriate to report a problem such as a missing file or wrong premise. Settlement is not a turn boundary; continue independent work per the receiver invariant below.

Defaults: a plain `tap send` is `settle-only` (digest-eligible, autosettle policy — the same stamp `--fyi` already produced); `--fyi` remains as a no-op alias of that default; `--note` asserts the same default explicitly and additionally skips the order-shape guard (below). A reply is requested with `--ask` (aliases `--reply` and `--expect-reply`), which stamps `reply=expected`. `--fyi` and `--ask` together are refused (`usage_error`, "pass either --fyi or --ask, not both") rather than resolved by precedence: the two flags name opposite intents, and silently honouring one would stamp the expectation the caller did not ask for. `--urgent` keeps its wake (it is not digest-eligible) but does not by itself request a reply. Sends from `--unattended` seats stay `settle-only` UNLESS the seat has a validated deliverable `reply_to` (§Reply routing) AND the send passes `--ask` / `--expect-reply`, in which case the grant transfers to the durable principal and the send stamps `expected` (tap-ywb v0.5, panel MUST-FIX 4 — the mere presence of a `reply_to` never changes a plain unattended send's default by itself). A registered `delivery: poll` sender's plain send is `settle-only`; it CAN discharge a reply by polling, so `--ask` / `--expect-reply` from a registered poll-mode `--from` stamps `expected`. The opt-in is explicit. A `reply`'s own outbound is `settle-only` by default (`--expect-reply` flips it) so two rule-following agents never ack-loop forever. `tap escalate` and `tap ask` are unchanged. An envelope with no `reply` field (v0.2 traffic) reads as `expected`.

### Speech-act verbs, `kind: order`, and the order-shape guard (v0.22, tap-oglkh)

The reply expectation above is a TRANSPORT property, but authors think in SPEECH ACTS. In one observed case a lead dispatched five work orders as plain settle-only sends and three recipients correctly refused them as notes: the obligation was a second, unrelated decision the author had to remember, and forgetting it is silent. Two additions close that gap. Every existing flag keeps its transport meaning — `--fyi` is still a no-op alias of the default, `--wake` remains an accepted note spelling; recipient read owns settlement — but the guard below does change one OUTCOME: a plain, `--fyi`, or `--wake` send whose body reads like a work order was accepted before and is refused now. That refusal is the feature, and it is the only behavior change to previously valid sends.

**`tap assign <to> -f <path>`** is exactly `tap send <to> --expect-reply --kind order`, with the ordinary delivery default. The internal flags are appended AFTER the caller's argv, and the send parser is last-write-wins, so the obligation and the kind are **invariant rather than overridable defaults**: `tap assign x -f b --kind discuss` still stamps `kind: order`. It refuses `--fyi` and `--note` (they name a note), and — because an assign caller never typed `--ask` — that refusal is raised BEFORE the generic note/ask conflict so the message never blames a flag the caller did not pass. `tap assign` already requests an answer; `--wake` is not an assignment flag. Arrival follows the shared composer policy. `tap assign` from a sender that cannot receive the answer — an unattended `--from` with no deliverable `reply_to` — is **refused rather than downgraded**, because the downgrade would produce `kind: order` with `reply: settle-only`: a payload asserting it is work while nothing tracks it. `tap send --ask` in that state keeps its existing warn-and-downgrade behavior.

`kind: order` is documented vocabulary only; general kinds have no semantic allowlist, while the reserved kinds retain their explicit transport rules (§Envelope).

**`--note`** asserts the message IS a note. It is settle-only (the default) and is the only EXPLICIT AUTHOR CONFIRMATION that clears the guard below — the other exemptions are structural (an obligation already tracked, a different advisory, a reply outbound), not a way for an author to assert intent. It is refused alongside every ask spelling (`--ask`, `--reply`, `--expect-reply`) and alongside `--fyi`, and it is rejected by the message-id `--reply-to` alias's send-only option gate (§Reply-to message alias) — otherwise the flag would be swallowed, `tap reply` would run, and the inbound would be SETTLED by a command the caller believed was a note.

**The order-shape guard.** A plain `tap send` whose BODY carries a bead id **and** a work-order marker is refused with exit 2 and `error_class=order_shaped_note` before any durable transport effect, naming two doors: `tap assign`, or `--note` to confirm it is a note.
